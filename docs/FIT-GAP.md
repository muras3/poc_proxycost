## 0. 結論 ── どれが一番いい形か

**どれか1つを採る、は誤り。3つは役割が違い、そのうち2つは既に互いに食い違っている（§4）。**

| | **A** 外部文書 | **B** コード | **C** マスタ |
|---|---|---|---|
| 料金の**値** | 弱い。行ごとの `tier` も `checked_on` も無い | **最強。**テストで固定され CI が通す | 強い。ただし手で保守され既に3行ずれた |
| 費目の**網羅** | **最弱。**19費目 | 中。Bが価格化しているものだけ | **最強。**F01〜F40 ＋ C/D の一覧 |
| 根拠の**追跡** | 出典URLはあるが行と紐づかない | コメントに原文。機械可読でない | **最強。**行ごとに `quote` / `inference_basis` / `source` / `checked_on` |
| **製品の向き** | **最強。**ループ、$3カート、収益、競合 | 無い | 無い |
| **実行可能性** | 無い | **唯一実行される** | `validate.py` のみ |

### 採る形

**値の最終権威は B（コード）。網羅と根拠の最終権威は C（マスタ）。製品の向きは A。**

**ただし現状の三者並立は維持しない。**このリポジトリで実際に起きた事故は、どれかが間違っていたことではなく
**3つがずれたこと**だった（§4 の3件、および `docs/MASTER.md` 自身が記録している「手書きは必ずずれる」）。

目標形は1つ:

```
master/fees.json + master/customs.json        ← 値と根拠の単一の出どころ
        │
        ├─ validate.py         rule を評価して実請求を再現（既にある）
        ├─ render-docs.py      docs/MASTER.md を生成（既にある）
        └─ **未実装**: services.ts の値がマスタと一致することを CI で突き合わせる
```

**`render-docs.py` が文書に対してやっていることを、コードに対してやっていないのが唯一の穴。**
この突き合わせが1本あれば、§4 の3件は書いた瞬間に CI で落ちていた。**最優先の1件はこれ。**

A（外部文書）は**リポジトリに取り込まない。**値を二重に持つ場所を増やすことになる。
取り込むのは §3 の差分だけで、取り込み先は C（マスタ）。

## 3. A が勝っている点 ── 取り込む

**3件。いずれも値そのものではなく、我々が持っていない観測。**

### ① FROM JAPAN の国内送料の既定は ¥700（社の公表値）

B は5社一律 `ASSUMED_DOMESTIC_SHIPPING_YEN = 800`（**我々の仮定**、tier `estimate`）。
A は FJ の公開計算機が **¥700 を default・editable** で出すと実測している。

**これは「社が自分で出している推定値」で、我々の仮定より出どころが強い。**
ただし**全社を ¥700 にするのは誤り**——FJ の値であって Buyee の実費レンジ（¥150–1,500）ではない。
**社ごとに「その社が自分で使っている既定値」を持つ欄を作る**のが正しい形。→ §5 T-F1

### ② 商品価格で利用可能な配送方法が変わる（FROM JAPAN）

A は FJ で**商品価格によって選べる method が変わる**ことを実測している。
B の `unavailableIn` は**国**でしか可否を持たない。**価格の軸が無い。**

`docs/TODO-NEXT.md` §0b が記録している**寸法の軸が無い**問題と同じ型の穴で、
どちらも「送れない便に値段を付ける」誤り。→ §5 T-F3

### ③ 製品の向き（A 独自・コード側に対応物が無い）

$3 Build my cart、Stripe の authorization→capture、affiliate との二層、競合（Otaku Shopping Guide）、
データフライホイール、プライバシーの線引き（「氏名を消しただけを匿名と呼ばない」）。
**ここは A がそのまま正しく、リポジトリに無い。**`REQUIREMENTS.md` §5（収益）と照らして別途起草する。

### A の P0 をそのまま実装してはいけない2件

| A の指示 | 実際 |
|---|---|
| 「FROM JAPAN Payment fee ¥200 → **¥0**」 | **¥0 にすると誤る。**ヤフオクの落札ごと ¥200 は現存（原文 per auction）。それ以外は 2023-01-31 廃止で、**出典のある ¥0** として行を残してある（消すと「調べていない」と区別が付かない）。A は店舗商品で実測したので Free が出たのが正しい |
| 「courier 料金は価格化できないという文言を訂正せよ」 | **訂正済み。**しかも A の理由（「非公開だから」の否定）より先へ進んでいる: ZenMarket の `POST /calc.aspx/Calculate` が便別 `Price` と `ShippingLimitsParamA/B/CInCm` を返すことを実測済みで、**真の障害は寸法が入力に無いこと＋通関が別モデルであること**と特定されている |

## 4. 新規発見 ── B と C が食い違っている3件

**A との照合より重いのはこちら。どちらも同じリポジトリの中にあり、同じ URL・同じ確認日を出典にしながら逆のことを言っている。**

### ① Neokyo の ¥350 に国内送料が含まれるか ── **最重要**

| | 主張 | 出典 |
|---|---|---|
| **C** `fees.json` F02 | ¥350 は `includes: ["domestic_shipping"]`、F13 国内送料は `zero / included_in F02`。**tier `A_confirmed`** | `neokyo.com/en/fees`、2026-09-07、quote「Order and domestic shipping price: 350 ¥JPY」「the order fee covers Shipping towards Neokyo」 |
| **B** `services.ts` | `domesticIncluded: false` | 同じ URL。COMPLETENESS A2 が「公式は（商品代＋国内送料）＋¥350 の構造で、¥350 の内訳に国内送料は無い」と判定 |
| **A** | ¥350 / Buy Request、国内送料は別途 | — |

**C の note には「`src/data.js` の `domesticIncluded: true` は正しい」と書いてある。**つまり C は
**コードを直す方向を指示していて、コードはその逆に直された。**

効く額は**1点あたり約¥800**。`COMPLETENESS.md` A2 が「**現在の『7カ国で Neokyo 1位』はこの仮定1つで作られている**」と
書いているとおり、**最もよく最安になる社の順位がこの1行で決まる。**Neokyo の実請求は0件で裏取りできない。

さらに**課金単位も三者で割れている**: C と B は「点ごと（同一商品の複数個は1回）」、A は「Buy Request ごと」。
1つの Buy Request に別々の商品を複数入れられるなら、B は Neokyo を過大に出している。

→ **一次情報の再取得が必要。これが最優先。**（§5 T-F4）

### ② FROM JAPAN の ¥500 は1つか2つか

C は **F02 取扱手数料 ¥500/点（A_confirmed）** と **F12 Product Protection Plan ¥500/点（B_inferred）** を
**別の行**として持つ ⇒ 合計 ¥1,000/点。
B は `perItemYen: 500` **のみ**で、コメントは「Protection Plan の ¥500/点 は既に service-fee として総額に入っている」と書く。
`docs/audit/fees.md` は B の ¥500 を `help_fee_140`/`help_fee_252` の **Plan Fee** に対応させている
（＝B の ¥500 は Protection Plan のほうで、**取扱手数料が落ちている**とも読める）。
A は「Product Protection / handling plan fee ¥500/item」と**1つとして**書く。

**B が正しければ C は ¥500/点 の過大、C が正しければ B は ¥500/点 の過小。**
FROM JAPAN は実測で1位になる国があるので順位に直接効く。→ T-F5

## 6. LLM の扱い ── 方針を更新した

これまでの約束は「**LLM は使わない**」（`README.md` / `REQUIREMENTS.md` §3）だった。
2026-09-10 にオーナーが範囲を確定した:

| 用途 | 可否 |
|---|---|
| 料金計算・重量推定・税額算定・順位づけ | **使わない。**従来どおり。非決定性が致命的で、価値の源が数字の正確さなので |
| **カート構築（$3 Build my cart）のエージェント** | **使う。**A §D5 の Playwright-first ＋ 失敗時のみ AI fallback |

**約束の書き方を変える:**「LLM を使わない」→「**計算に LLM を使わない。実行時に計算結果を左右する推論 API を呼ばない**」。
カート構築は計算エンジンの外側の別プロセスで、総額・順位・差額のどの数字にも触れない。
