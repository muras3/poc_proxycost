## 1. 現状: 何がどこにあるか（正確な記述）

### 1.1 `maxGramsFor` は郵便専用。宅配便には同種の関数が無い

```ts
// src/lib/pricing/postage.ts
export function maxGramsFor(method: PostalMethod, cc: CountryCode): number {
  if (method === 'ems') return EMS_MAX_GRAMS;
  const steps = TABLES[method][POSTAL_ZONE[cc]];
  return steps ? steps[steps.length - 1]![0] : 0;
}
```

引数の型が `PostalMethod`（日本郵便の5方式）だけで、`CourierMethod`（DHL/UPS/FedEx/ECMS 等）は受け取れない。`src/lib/pricing/` のどこにも「運送会社の重量上限」という概念自体が存在しない——郵便には公表された地帯別料金表という一次情報があり、表の最後の段の重量がそのまま「表の外は送れない」の意味を持つ（`postageFor` のコメント「表の外は『高い』ではなく『送れない』」）。宅配便にはこの表が無いので、`maxGramsFor` を宅配便に拡張しようにも受け皿となるデータ構造から無い。

`splitByWeightLimit`（`parcels.ts`）は `maxGramsFor` の値を受け取って個口を分割する汎用関数で、関数自体は郵便専用ではない。だが呼び出し側（`compare.ts` の `methodBoxes`）が

```ts
// courier-clearance.ts のコメントが指摘する通り
isCourier ? baseBoxes : boxesForPostal(...)
```

という分岐になっており、**宅配便は常に `baseBoxes`（店舗単位の下地、未分割）を使い、`splitByWeightLimit` を一切通らない。** これは実装漏れではなく明示的な分岐で、`courier-clearance.test.ts` が「宅配便の箱の `ParcelSplitReason` が `'weight-limit'` になることは今のコードでは起こり得ない」ことをピン留めしている。つまり§2④の分割ロジックは**存在してはいるが、宅配便向けの入口が用意されていないので発火しない**——CLAUDE.md §9 が記録した通り、これは「原則としての決定」ではなく単に配線されていないだけ。

### 1.2 「20kg」がコードのどこに、どういう意味で入っているか

`20000`(g) は `src/lib/pricing/services.ts` の宅配便テーブル（`MeasuredPostageRate.usGrid` 相当、`{ g: 20000, yen: ... }` の形の配列）に**測定点の1つとして**現れる。この列に付いたコメント（`services.ts` 316行目付近）:

> 既定の箱（20×15×10cm）でだけ測った11点（500/600/700/1000/1500/2000/2500/3000/5000/10000/**20000**g）。点と点の間は補間しない。**測定範囲の外（500g未満・20000g超）は `null`。外挿しない。**

つまり **20kg は「運送会社が公表した上限」ではなく「代行各社の見積もりサイトで実測を止めた重量」**——単なる測定レンジの天井であって、それより重い荷物を運送会社が拒否する根拠にも、受け付ける根拠にもならない。`courier-wiring.test.ts` のコメント「20,000g で FedEx Economy が逆転する」も、この測定点での逆転の話であり、上限の話ではない。

`maxGramsFor` 側の20kg相当の数字（郵便の国際小包30kg等）とは**性質が全く違う**——郵便側は公表料金表の最終段（一次情報）、宅配便側は自分たちが測定を打ち切った点（実務上の都合）。この2つを同じ「20kg」という数字の並びで見て混同したのが、CLAUDE.md §9 の1回目の誤答（「実測レンジの天井を公表された上限として誤用しないための原則的決定」）の元。**実際には決定は無く、単に混同されていただけ**——PR #109 の一次資料調査で初めて宅配便側の実際の上限（DHL 70kg・UPS 70kg 等）が判明した。

| 運送会社 | 1ピース上限を超えたら | 確度 |

## 2. 「分割」と「サーチャージ」を分けて設計する

### 2.1 原則

`docs/DESIGN-BOX-SIZE.md` §2④の「上限を超えたら箱を分割する」は、**日本郵便のように上限超過＝物理的に送れない**ケースにだけ正しい。DHL・UPS(US/CA/AU/GB)のように**上限超過＝追加料金を払えば同じ1箱のまま送れる**ケースに分割を適用すると、ユーザーに嘘の見積もりを出す——実際は1箱・サーチャージ込みの価格で送れるのに、2箱分の送料（多くの場合サーチャージより高額）を提示することになる。したがって:

- **分割（`splitByWeightLimit` を宅配便の便にも通す）** は「上限超過＝拒否」の便にだけ適用する。
- **サーチャージ（新設の加算ロジック）** は「上限超過＝追加料金」の便に適用する。

### 2.2 サーチャージのモデル（提案）

`PostageRateCommon`（`services.ts`）と同じ考え方で、`MeasuredPostageRate` に次のような器を追加することを提案する（**設計案。今回のPRでは実装しない**）:

```ts
interface OverweightSurcharge {
  /** 1ピースあたりの上限（超えたらサーチャージが発生する境界）。 */
  perPieceMaxGrams: number;
  /** サーチャージの通貨建て金額。円へは rates.ts の rateFor() を通す。 */
  amount: { currency: 'USD' | 'EUR' | ...; value: number };
  perPieceOrPerShipment: 'per_piece' | 'per_shipment';
  tier: Tier;
  sourceUrl: string;
  checkedOn: string;
  /** 為替換算した円額であることを画面に明示する一言。 */
  note: string;
}
```

**為替が絡む**: DHLのサーチャージはUS $100・DE €100/€50のようにドル・ユーロ建てで、円への換算が要る。`rates.ts` は既に `rateFor(ccy)` で円建てレートを持っており（ECB由来、`RATES_SOURCE_URL`）、これがそのまま使える——ただし `rates.ts` は現在「送料・手数料の外貨建て公表額を円に換算する」用途で使われており、**サーチャージという新しい費目の種類にも同じ変換を適用してよいかは設計判断が要る**（既存の費目と同じ`checkedOn`規律・同じ「換算日を額と同じ重みで扱う」原則を踏襲すべき、という以上のことはここでは決めない）。

### 2.3 UPS Singapore の扱い（断定できない。両案を示す）

一次資料が2つに割れている:
- **US/CA(レートガイド)・AU/GB(共通Terms and Conditions of Service)**: 「Over Maximum Weight/Length/Sizeの追加料金の対象」——サーチャージ方式。
- **SGのService Guide**: 「not accepted for transportation」——拒否方式。

`master/carrier-weight-limits.json` の `conclusions` (`W2_ups_mixed_refused_and_surcharged`) はこの矛盾を「解けていない」と明記しており、以下は**推論であって確定ではない**:

> 法的なTerms文書は「検知されれば課金する（実運用でも受け付けてしまう）」という運用実態を書き、顧客向けService Guideは「そもそも超えるものは送るな」という案内を書いている、という整理があり得る。

**断定できないので両案を示す:**

| 案 | 内容 | 根拠 | リスク |
|---|---|---|---|
| **A: 法的Termsを優先** | UPSはSGでも実際にはサーチャージ扱いとして統一する | Terms and Conditions of Service は契約文書であり、Service Guideより拘束力が強いと一般に解釈される | Service Guideが「引き受けない」と明記している以上、実際に窓口で拒否される可能性がある。ユーザーに「送れる」と見せて実際には送れないと、過小評価どころか誤情報になる |
| **B: 安全側に倒しSGだけ分割/不可** | SGだけ「UPSでこの重量は選べない」として扱う(郵便の`unavailableIn`と同じ形で表現できる) | 顧客向け文書が最終案内である可能性が高く、実際の窓口対応に近いと考えられる | US/CA/AU/GBとロジックが割れ、UPSという1つの運送会社の中で国によって挙動が変わることの説明コストが画面に乗る |

判断材料: SGのService Guideは「顧客向け」であり、実際にラベル発行の窓口(代行のUPS契約)で拒否されるかどうかを最終的に決めるのはこの文書である可能性が高い——ただしこれも一次資料自体が明言しているわけではなく、**このリポジトリの調査だけでは決着しない。実際のUPS SG窓口での挙動確認（別途の実測）が無い限り、A/Bどちらかを選んだ時点でそれは「未検証の運用判断」になる**（`courier-clearance.ts` の「working treatment」と同種の性質）。

### 2.4 FedEx をどうするか（3案とユーザーへの見え方）

一次資料に到達できない(`input_rejected`, 全7カ国)。

| 案 | 内容 | ユーザーへの見え方 |
|---|---|---|
| **① 上限を持たないものとして扱う** | 超過しても何も起きない(現状通り) | 何も表示されない——ユーザーは上限が本当に無いのか、単に確認できていないだけなのか区別できない。**根拠の無い「安全」を暗黙に主張することになる** |
| **② 他社の値を借りる** | DHLかUPSの70kgをFedExにも適用 | 画面に出す数字自体に根拠が無い。**採るなら「これはFedEx自身の資料ではなく他社の値を借用した推定である」とnoteに明記する必要がある**——`courier-clearance.ts` の `unitConfidence: 'inferred'` と同じ扱いに倣うべき |
| **③ その重量ではFedExを比較対象から外す (`comparable: false`)** | 上限が分かっている重量帯を超えたらFedExの行を「確認できていないため比較対象外」として出す(額を出さない、消さない) | `docs/PRINCIPLES.md` 原則2(「額不明の行は消さず null で出す」)と整合する。ユーザーには「FedExの重量上限は未確認のため、この重量ではFedExを比較に含めていません」という一言が要る |

**③が最も原則に合う**——「分からない」を「安全」にも「危険」にも倒さず、比較不能として開示する。①は無限にトラブルの少ない上限を暗黙に主張してしまう点でCLAUDE.md §9が禁じる「状況を理由にする」ことに近い。②は数字自体を捏造することになるので、採用するとしても明示のラベル付けが必須。

### 2.5 ECMS をどうするか

「公表していない」は「上限が無い」ではない。ECMSはパートナー配送業者(現地の宅配業者)に実際の配送を委託していると考えられ(T&C自体はそう明言していない——推論に留まる、`master/carrier-weight-limits.json` `conclusions.W5`)、**独自の上限を持たない代わりに、委託先の上限を実質的に継承している可能性がある**が、これも一次資料が確認していない。

提案: FedExと同じ③(comparable: false)を採用しつつ、noteの文言をFedExとは分ける——FedExは「到達できていない(WAF)」、ECMSは「自社の上限を公表していない(確認はできたが、無い)」という**確認できた不在(counted_absence)**と**確認自体ができていない(input_rejected)**の違いをユーザーに伝える。この2つを同じ「データなし」の一言で片付けると、確認の努力量の違いが消えてしまう。

## 3. ネットワーク上限(1,000kg/300cm)を実装すべきか

現在の想定最大重量は20kg(仮置き)。DHLのネットワーク上限は1,000kg/300cmで、想定重量の50倍。**この上限に到達する条件は、20kgという仮置きがそのまま維持される限り実務上ゼロ**。

判断: **今は実装しなくてよい。** 理由は「到達しないから要らない」という単純な話ではなく、以下の条件付き:
- 20kgという仮置きは「今どこにいるかの記述であって、それより重い荷物が発生し得ないことの証明ではない」(CLAUDE.md §9と同じ論理)。**将来、ユーザーが寸法・重量を自由入力できるようになった時点(`docs/ROADMAP.md` P2)で再検討が必要**。
- 現時点で実装しても、テストする実測データが無く(20kg超のプロキシ計算機実測は行っていない)、「検査が検査になっていない」型の器になるリスクがある(Fableが過去に見つけた欠陥と同型)。
- 安全網として**コメントに明記して残す**ことは推奨する——「1,000kg/300cmのネットワーク上限は未実装。現在の20kg仮置きの範囲では到達しないため。仮置きが外れたら要再検討」という一言を、`postage.ts` の `DEFAULT_PARCEL_DIMENSIONS_CM` 周辺のコメントに加える案。

## 4. どの条件で総額が動くか(見積もり)

対象範囲: 7カ国(US/GB/DE/FR/AU/CA/SG) × 現在サイトが扱う重量帯 × 4社(DHL/UPS/FedEx/ECMS)。

前提: 現在の既定箱は20×15×10cm固定(`DEFAULT_PARCEL_DIMENSIONS_CM`)、宅配便の実測レンジは500g〜20,000g(`services.ts` のコメント、`courier-wiring.test.ts`)。**このサイトが実際に価格を出している宅配便の重量域の上限は20,000gで、DHL/UPSの1ピース上限(70kg=70,000g、USのDHLは68kg)を大きく下回る。**

したがって:

- **DHLの1ピース上限(68〜70kg)・UPSの1ピース上限(70kg)のどちらも、現在のサイトが実際に価格化している重量域(〜20kg)には一度も到達しない。**
- **結論: 現在の想定範囲(20kg以下)では、このサーチャージ/分割モデルを実装しても総額は1円も動かない。**

これは「実装を急ぐ必要が無い」ことを意味する重要な結論であり、CLAUDE.md §8(数値を動かす変更とUIを動かす変更を混ぜない)の観点からも、**このPRで設計だけを出しsrc/master/には触れない**という今回の指示は妥当——実装しても現状の計算結果に差分が出ないため、実装のタイミングは「20kg仮置きが外れる(ユーザー入力の寸法・重量が拡張される)」タイミングと合わせるのが合理的。

ただし1点、**今の20kg仮置きの外側で意味を持つケースが1つある**:UPS Singaporeを「拒否」(案B)で扱う設計を採る場合、それは重量の大小に関わらず「UPS×SG」という組み合わせ自体をどう見せるかの設計であり、70kgという上限値には依存しない。この点だけは20kg以下の範囲でも(理論上)効きうるが、**実際に70kgという上限自体は現状のUI入力(重量)ではユーザーが到達できない**ため、「UPS SGは常に拒否/常にサーチャージ」という二択の議論には影響しない——上限に達すること自体が今のサイトでは起こらない。

## 5. `docs/DESIGN-BOX-SIZE.md` §2④ 書き換え案(文書自体は書き換えない。案として提示)

現行の§2④は「上限を超えたら箱を分割する」を単一のルールとして書いている。案:

1. **タイトルを「上限超過時の扱い」のように一般化**し、「分割」と「サーチャージ」の2つの下位ルールに分ける。
2. **郵便(`PostalMethod`)**: 現行のまま。「表の外は送れない」ため分割が正しい(変更なし)。
3. **宅配便(`CourierMethod`)は運送会社ごとに扱いを分ける**:
   - DHL: サーチャージ(1ピース上限超過時、Overweight Pieceサーチャージ。ネットワーク上限1,000kg/300cm超は拒否/分割——ただし現状の想定重量では到達しない、と明記)
   - UPS: US/CA/AU/GBはサーチャージ、SGは**未決定(A/B案のどちらを採るか、オーナー判断待ち)**
   - FedEx: 上限データ無し。`comparable: false`で比較対象から外す(理由を画面に表示)
   - ECMS: 自社上限の公表無し。FedExと同様`comparable: false`だが、noteの文言は「到達できていない」ではなく「公表していない」で区別する
4. **20kgという数字についての注記を追加**:「20,000gは運送会社が公表した上限ではなく、現在サイトが宅配便の価格を測定しているレンジの天井(実測の都合)である。上限そのものはこの文書の別表(PR #109調査、`master/carrier-weight-limits.json`)を参照」。
5. **ネットワーク上限(1,000kg/300cm等)は現時点で未実装であることと、その理由(現在の20kg仮置きの範囲では到達しない)を明記**——「実装していない」を「上限が無い」と読まれないようにする一言。

## まとめ(報告用の要点)

- **20kgの意味**: `services.ts` の宅配便テーブルで測定を打ち切った点(実測レンジの天井)であり、運送会社の公表上限ではない。`maxGramsFor`(郵便専用、公表料金表の最終段)とは性質が別。
- **分割とサーチャージの切り分け**: 郵便=分割(変更なし)。DHL=サーチャージ(1ピース上限超過)、ネットワーク上限(1,000kg/300cm)超は拒否だが現状の重量域では到達しない。UPSはUS/CA/AU/GBがサーチャージ、SGだけ拒否の可能性——**一次資料同士が矛盾しており断定できない**。
- **UPS Singapore**: 断定できない。A(法的Terms優先・サーチャージ扱い)とB(安全側・拒否扱い)の両案を提示。実際の窓口挙動の確認が無い限りどちらも「未検証の運用判断」。
- **FedEx**: 一次資料に到達できず(WAF)全7カ国データ無し。3案のうち`comparable: false`(比較対象から外し理由を画面表示)が原則2と最も整合。
- **ECMS**: 自社上限を公表していないことを確認済み(counted_absence)。FedExと同じ`comparable: false`寄りだが、「未確認」と「確認したが無い」の違いをnoteの文言で区別すべき。
