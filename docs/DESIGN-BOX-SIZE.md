作成日 2026-09-12 / 状態: **設計のみ。実装はしていない。** データ構造（`src/data/density.ts`）は
このPRで新設したが、`compare.ts` の計算にはまだ繋がっていない。

（`resolveWeight` の解決の仕方）、`master/courier-rates.json`（実測データ、寸法走査を含む）、
`docs/audit/o2-courier-2026-09-08.md`（§5 が自身の方法上の欠陥を書いている手本）、
`docs/ROADMAP.md` P2、`docs/DESIGN-FEES-DATA.md` / `docs/DESIGN-WEIGHT-MATCH.md`（体裁）、

## 0. 背景（オーナー確定 2026-09-12）

宅配便は容積重量で課金される。箱の大きさが要る。いまのコードは箱を20×15×10cm固定にしていて、
点数にも商品にも反応しない。5点でも1点でも同じ箱では、宅配便を価格化できない。

商品ごとの寸法は集められない。重量は Shopify の `products.json`（`grams`）から
`src/data/weights.ts` のカテゴリごとに揃っているが、Shopify の標準データに寸法は無い。

**代わりに「密度」を持つ。**

```
体積 = 梱包後重量 ÷ 密度
```

重量は既にカテゴリごとに揃っているので、カテゴリごとに密度を1つ足せば体積が出る。

### いま手元にある根拠（少ない）

| 出所 | 重量 | 体積 | 密度 |
|---|---|---|---|
| **実請求1件**（ZenMarket / DE / 2026-05、7点、42×31×24cm） | 3,210g | 31,248cm³ | **0.103 g/cm³** |
| 1/7スケールフィギュア（`src/data/weights.ts` の1,500gと、箱30×20×25cmの**仮定**） | 1,500g | 15,000cm³ | **0.100 g/cm³** |

**2点目の箱の寸法はコーディネーターの仮定であって一次情報ではない。** 実請求のカテゴリ内訳
（7点の中身）も記録が無く、密度0.103はどのカテゴリにも帰属できない「カテゴリ不明の
カート全体」の値でしかない。**根拠は事実上ゼロ件**というのが正直な現状で、1点目は
「実請求だがカテゴリが分からない」、2点目は「カテゴリは分かるが箱が仮定」という、
互いに補えない2つの弱さを持つ。

## 1. 最優先の要件: 較正が増えるほど精度が上がる設計にする

**オーナー指示（2026-09-12追加）**: 密度を「いま置く定数」として設計してはいけない。
実データが増えるたびに自動的に精度が上がる仕組みが、初期値そのものより重要。

### 1.1 較正の入力を貯める場所 ── `CalibrationInvoice`（`src/data/density.ts`）

実請求（梱包後重量と実際の寸法が両方分かっているもの）を1件ずつ持つ配列
`CALIBRATION_INVOICES` を新設した。各要素は:

```ts
interface CalibrationInvoice {
  id: string;
  source: string;          // 'ZenMarket / DE / 2026-05' のような出所
  obtainedOn: string;
  categoryMix: 'unknown' | Partial<Record<string, number>>;  // カテゴリ内訳。分からなければ 'unknown'
  packedWeightG: number;
  dimsCm: BoxDimsCm;
  isPrimarySource: boolean;  // 寸法が実請求の記載か、仮定か
  notes: string;
}
```

`categoryMix` を `'unknown'` として明示的に許すのは、**いま手元の唯一の実請求がまさに
それ**だから。カテゴリが分からない実請求を無理に按分せず、「カテゴリ不明のカート全体」用の
別枠（`GENERAL_MIX_DENSITY`）に落とす。`isPrimarySource: false` の1件（フィギュアの仮定箱）は
較正件数に数えない ── 一次情報でない値を較正1件として水増ししない。

### 1.2 何件で較正されているかが読めること ── `CategoryDensity.n`

`src/data/weights.ts` の `WeightLine` が `n` / `p25` / `p75` / `spread` を持つのと同じ形で、
`CategoryDensity` も同じ語彙を持つ:

```ts
interface CategoryDensity {
  category: string;
  densityGPerCm3: number;
  n: number;                      // 較正に使った実請求の件数
  p25?: number;
  p75?: number;
  tier: 'A_confirmed' | 'B_inferred' | 'C_unknown';
  provisional: boolean;           // n=0 またはオーダーだけで決めた値なら true
  basis: string;                  // 数字の理由を文章で
  calibrationInvoiceIds: string[];
}
```

**1件で決めた密度と20件で較正した密度は、`n` を見れば区別できる。** いまの11カテゴリは
全件 `n: 0` / `provisional: true` ── これは較正されていない置き物であることが型を見ただけで
分かる状態で、値そのものの見た目（小数点以下の桁数など）で区別させない。

### 1.3 予測と実際のずれを測れること ── `DensityPredictionCheck`

```ts
interface DensityPredictionCheck {
  invoiceId: string;
  category: string;
  densityUsedGPerCm3: number;
  predictedVolumeCm3: number;
  actualVolumeCm3: number;
  errorPct: number;   // (predicted - actual) / actual * 100
}
```

`checkPrediction()` がこれを計算する関数として `density.ts` にある。**`docs/ROADMAP.md` P4-4c
（実請求検証、現在0件）が求めているのはまさにこれ**——実請求が新しく来るたびに、その時点の
`CategoryDensity` で体積を予測し、請求書の実寸と突き合わせて誤差を記録する。この仕組みが
無ければ「精度が上がった」と主張する根拠が無い。**この PR ではまだ何もこの関数を呼ばない**
（呼び出し側・記録先はまだ無い）——器だけを先に置く。

### 1.4 増えたときに何が起きるか（数字で決める）

**カテゴリ分けの単位**: 較正はカテゴリ単位で貯める。カテゴリを跨いで密度を使い回さない
（`GENERAL_MIX_DENSITY` はカテゴリが分からないときの器であって、カテゴリ別の値の代用ではない）。

**tier が上がる条件**（`src/data/weights.ts` 系列の既存の閾値をそのまま借りる ──
`docs/DESIGN-WEIGHT-MATCH.md` §0.4 の「新しいラインは P75/P25 ≤ 3 かつ n ≥ 50」と同じ発想だが、
密度の較正は実請求という重いコストの一次情報なので、閾値はもっと小さく置く）:

| 条件 | tier |
|---|---|
| `n = 0`（実請求なし。順序だけで置いた値） | `C_unknown`、`provisional: true` |
| `n = 1`（実請求1件） | `C_unknown`、`provisional: false`（値そのものは実データ由来だが、1件では較正と呼ばない —— 1件の箱の詰め方の癖をカテゴリ全体の値にしていいか分からない） |
| `n ≥ 3` かつ `spread(p75/p25) ≤ 3` | `B_inferred`（複数件が同じ数倍の範囲に収まった。傾向として使ってよいが幅で扱う） |
| `n ≥ 8` かつ `spread ≤ 2` | `A_confirmed`（十分な件数が狭い範囲に収まった） |

**p25/p75 を持たせるのはいつからか**: `n ≥ 3` から。2件では四分位に意味が無い
（`src/data/weights.ts` の `WeightLine` も `n` が数十〜数千のラインでのみ `spread` を根拠にしている）。

**この仕組みはまだ「動く」わけではない**——`n` を数えて `tier` を上げる処理は
`density.ts` にまだ実装していない（手で数値を書き換える運用を想定した最小の器。
較正が実際に増え始めたら、`weights-build.ts` のようなビルドスクリプトへ切り出すことを検討する、
と `density.ts` 冒頭のコメントに書いた）。

## 2. 算出ロジック

### ① 梱包後重量

```
packedG = round(Σ(商品重量) × 1.2 + 300)
```

既存（`compare.ts` の `grossG`）。**変更なし。**

### ② 体積 ── カートに複数カテゴリがあるときの合成

```
volumeCm3 = packedG ÷ density
```

複数カテゴリがカートにあるとき、**カテゴリごとに体積を出して足す方式を選ぶ**
（重量の加重平均で単一の密度を作る方式は採らない）。理由:

- 体積は加法的だが、密度は加法的ではない。フィギュア3個+トレカ2枚を「平均密度」で
  ひとつの塊として扱うと、実際には別々の物として梱包される2つの体積の和とズレる
  （加重平均密度で割った体積は、個別に体積を出して足した値と一致しない——調和平均を
  取らない限り一致せず、密度の加重平均は単純平均であって調和平均ではない）。
- カテゴリごとに体積を出す方式なら、①のカテゴリ別重量分解（`src/data/weights.ts` の
  `resolveWeight` が既にカテゴリ単位で重量を返している）とそのまま接続できる。

### ③ 箱の形 ── 立方体を選ぶ

体積から3辺を出す方法は2つ検討した:

- **実請求の比率**（42:31:24 ≒ 1 : 0.74 : 0.57）を使う
- **立方体**（∛volume）にする

**立方体を選ぶ。** 実請求は1件しかなく、その比率を一般化してよいかは疑わしい。42:31:24 という
比率は、その荷物の商品構成・代行の梱包方針・たまたま在庫にあった箱のサイズに左右されている
可能性があり、「宅配便の箱は一般にこの比率」と言える根拠が無い。1件のデータから形状まで
借りるのは過学習に近い。立方体は**形状について何も仮定しない**という意味で最も保守的な選択で、
根拠が薄いときの既定として妥当。

較正が増えて（`n ≥ 8` 相当）複数の実請求の比率が近い範囲に収まってきたら、比率方式への
切り替えを再検討する余地はあるが、**それは将来の話であり、いまは立方体。**

### ④ 分割 ── 方式の上限を超えたら箱を増やす

- 重量: 小形包装物2kg / EMS・国際小包30kg
- 寸法: 最大長 / 長さ+胴回り / 3辺の和 ── **別PRで実装中**（`postage.ts`/`services.ts`。
  このPRでは触らない）

このPRは①〜③の器だけで、④の分割ロジックには接続しない。

### ⑤ 各箱の申告額 ── 均等割をやめる

いまのコード（`compare.ts`）は `itemsYen / parcels` で均等割している。**これは根拠が無い。**
実際には箱の中身の合計金額が申告される。

**割り当て規則: 重い順に詰める。** 候補は「重い順」「体積の大きい順」「入力順」の3つを検討した。
重い順を選ぶ理由:

- 梱包後重量は既に商品ごとに分解できている（`resolveWeight` がカテゴリ単位・重量表単位で
  グラムを返す）ため、追加のデータ（体積・入力順への依存）を必要としない。
- 「重い順に箱を埋める」は現実の梱包作業に近い直感（重い物を先に箱の底に置く）で、
  ビンパッキングの初等的なヒューリスティック（First Fit Decreasing）とも一致する。

**ただし実際の割り当ては代行が決める。これは仮定である。** 代行がどの商品をどの箱に
詰めるかを我々は知りようがなく、この規則は「宅配便が箱ごとの申告額を要求する」という
制約を計算上満たすための**仮の規則**でしかない。均等割よりは実態に近いはずだが、
実際の申告額とズレる可能性は残る。

**傍証（`master/fees.json` F39c、2026-09-12）**: ZenMarketの発送案内ページ自体が、
複数口になったとき商品が物理的に箱ごとに分かれることを説明している。

> "Split items in two or more parcels ... Each parcel will be treated as a separate
> one ... Example ... A and C are placed into parcel #1 and B into parcel #2."
>
> 出所: https://zenmarket.jp/en/shipping.aspx（確認日 2026-09-12）

**この傍証が示すのはここまで**: 商品が箱ごとに物理的に分かれる、という**分割の事実**
だけである。**申告額をどう計算するかはこのページのどこにも書かれていない。** 「重い順に
詰める」という本節の割り当て規則を裏付けるものではなく、「均等割ではなく商品ベースで
割れる」という方向性を支持する状況証拠に留まる。F39cのステータス（`C_unknown`、
代行5社共通）はこの傍証によって上がらない ── ステータスの管理は `master/fees.json`
を編集している別のエージェントの管轄であり、本ドキュメントはそれを先取りしない。

同じページには、申告額の按分そのものとは別に、しきい値の扱いに関わる記述もある
（⑤の答えではなく隣接情報として記録する）:

> "If multiple parcels addressed to the same recipient arrive in Australia on the
> same plane, and their total price exceeds 1,000 AUD, they may be treated as a
> single parcel."

これは「同じ受取人・同じ便に複数口が届くと、豪州側で合算してしきい値判定される
場合がある」という話で、各箱の申告額の計算方法とは別軸（免税枠のしきい値ロジック）
の情報である。

**実装状況（2026-09-12時点）**: この規則は**決定・文書化済みだが未実装**である。
`compare.ts` は現在も `itemsYen / parcels` で均等割を計算しており、本節の規則には
まだ繋がっていない。実装は、同じファイル（`compare.ts`）を触る進行中の配送方法
（courier）配線変更の後ろに列を作って待たせる ── 同じ箇所を同時に書き換えると
競合するため。**この文書を読んで「もう均等割ではなくなっている」と早合点しないこと。**
文書化された規則とコードの実際の挙動がずれる、というまさにこの失敗を本リポジトリは
今日すでに一度、別の場所（ROADMAPの記載が実装より先行していた件）で起こしている。

### ⑥ 寸法が不明なときの既定 ── 大きい方を仮定する（オーナー確定 2026-09-12・4つ目の規則）

①〜⑤は密度モデルそのものの設計。ここは、その密度モデルを当てはめてもなお寸法が
決められない場面（較正が薄い、カテゴリが混在している、等）で、**どちら側に倒すか**
を決める規則。これまでの合成方式（②）・箱の形（③）・申告額の割り当て（⑤）に並ぶ、
4つ目の設計判断として記録する。

**規則: 寸法が分からないときは、小さい箱ではなく大きい箱を仮定する。**

根拠は2つある。

1. **ZenMarketの公開見積もりツール自体がそう振る舞っている。** 寸法欄を空欄にした場合と、
   同じ600gで20×15×10cmを入力した場合を比較すると、空欄の方が高い運賃を返す
   （NOVA GLOBAL: ¥3,134 [空欄] vs ¥2,302 [20×15×10cm]、ECMS EXPRESS: ¥4,692 vs ¥3,230）。
   つまり代行会社自身のシステムが「寸法未記載」を「容積重量の課金なし」ではなく
   「より大きい体積を仮定する」側として扱っている。出所: ZenMarket計測データセット
   （2026-09-11、ブラウザUI経由で取得）の `cross_check.no_dims_vs_baseline` の記録。
   ただし同じ計測で DHL GREEN+ / FEDEX LOWCOST / FEDEX / UPS はこの重量で差が出ておらず、
   **効果は方式（配送方法）依存であって全方式共通ではない。** ここは誇張せずそのまま書く。
2. **オーナーの判断（2026-09-12）**: 見積もりが実際の請求より低く出ることは、高く出ることより
   信頼を損なう。高めに見積もって実際は安かった、という外れ方の方が安く済む間違いである。

**この規則が許可しないこと**: 数値を根拠なく水増ししてよい、という話ではない。仮定する箱は
あくまで本ドキュメントのカテゴリ密度モデル（§1・§2）から出た値であり、規則4が決めるのは
「情報が足りず決め切れないときにどちら方向へ寄せるか」というタイブレークだけである。
そうして出した推定値は、他の推定と同様に**利用者には「推定である」と明示して見せる**
（§3・§5参照）。実測値であるかのように見せてはならない。

## 3. 利用者が箱の寸法を触れないこと（オーナー確定 2026-09-12・重要な禁止事項）

**箱の寸法は、重量と扱いを分ける。利用者が入力・上書きできる形にしない。**

| | 重量 | 箱の寸法 |
|---|---|---|
| 誰が決めるか | 商品の事実。利用者が調べられる | 代行が梱包時に決める。利用者は知りようがない |
| 利用者の入力 | 精度が上がる（実際の値を知っているから） | 精度が下がる（根拠の無い希望になる） |
| 現在の実装 | 推定値を出し、上書きできる。出所と`~`の印つき | 固定値20×15×10cm |
| **あるべき形** | **現状のまま** | **完全に我々の推定。入力欄を作らない** |

理由:

1. **利用者は注文の時点で箱を知らない。** まだ梱包されていない ── 重量と違い、
   利用者が「本当の値」を知っている場面が存在しない。
2. **入力できると、実際より小さい値を入れて総額を安く見せる道具になりうる。** 「小さい箱に
   すれば安くなる」と気づいた利用者が、根拠の無い希望値を入れれば、こちらが過少な総額を
   出す片棒を担ぐことになる。

**「詳しく指定する」のような折りたたみの中に入れるのも駄目。** 入力欄自体を作らない。
密度モデルによる推定は、**利用者に見せるのは「これは推定である」という注記だけ**で、
数値を直接動かす手段を与えない。

次にこの設計を読む人が「重量が上書きできるのだから箱もできるようにしよう」と考えないよう、
**重量と箱は同じ画面に並んでいても対称ではない**、とここに明記する。

**利用者が間接的に影響できるものは別。** まとめ発送を頼むかどうかは利用者が選べる
（既にBuyeeの「既定」と「まとめ」の2行で表現している——`services.ts` の `consolidationOnRequest`
系）。これは箱の「数」に効くが、箱の「寸法」を指定しているわけではない。区別する。

## 4. 弱点（正直に書く。`docs/audit/o2-courier-2026-09-08.md` §5 と同じ水準を目指す）

- **密度の根拠が実質1件の実請求、しかもカテゴリ不明。** ZenMarket/DE/2026-05の1件は
  カテゴリ内訳が記録に無く、どのカテゴリの密度にも使えない。使えたのは
  「カテゴリ不明のカート全体」という一段抽象化した器（`GENERAL_MIX_DENSITY`）のみ。
- **2点目（フィギュア0.100g/cm³）の箱寸法は一次情報ではない。** コーディネーターの仮定
  （30×20×25cm）であり、実請求の記載ではない。較正件数（`n`）にも数えていない。
- **カテゴリごとの密度11件は較正されていない。** すべて `n: 0` / `provisional: true`。
  値は「この順に高いはず・低いはず」という物理的な順序づけから当てはめた**当てずっぽう**で、
  実測でも統計でもない。順序の理由（紙は密度が高い、シューボックスは空隙が多い、等）は
  `src/data/density.ts` の各エントリの `basis` に書いたが、**数値自体を信用してはいけない。**
- **箱の形の仮定（立方体）。** 実請求1件の比率（42:31:24）を一般化する根拠が無いため
  立方体にしたが、立方体もまた「形について何も知らない」という開き直りであって、
  実際の宅配便の箱が立方体に近い保証はない。
- **商品の割り当て（重い順）は代行が決めるので、我々の規則とは違いうる。** 実際にどの商品が
  どの箱に入るかは代行の裁量で、我々の「重い順」はその代替に過ぎない。
- **実データでの検証は後の段階で行う予定。** `DensityPredictionCheck` という器は用意したが、
  この PR ではまだ何も検証していない。今のところ較正1件・検証0件。
- **カテゴリ密度の合成方法（②の「足す」方式）自体も未検証。** 複数カテゴリを混載した実請求で
  この合成が実際の体積にどれだけ近いかは、まだ1件も確かめていない。

## 5. 利用者への開示の文案

既存の開示（重量の推定、宅配便が未価格化）と同じ調子で:

> 箱の大きさは、商品の重さと種類から推定しています。実際の箱は代行会社が決めるため、
> これと異なる場合があります。

補足が要る場面（密度の根拠が薄いことまで示したいとき）向けの長い版:

> 箱の大きさは、商品の重さと種類（カテゴリ）から推定した密度をもとに計算しています。
> この密度はまだ実際の請求書1件分でしか確かめられておらず、多くのカテゴリでは
> 確からしい順序（重いか軽いか）だけを頼りに仮の値を置いています。実際の梱包は
> 代行会社が決めるため、これと異なる場合があります。

**申告額の割り振り（箱が複数になったとき）についても、同じ調子で文案を置く。**

短い版:

> **箱を何個に分けるかは代行会社が決めます。私たちはそれを知ることができないため、次の前提で仮に分けて計算しています。**
>
> - 配送方式の上限を超えたら箱を増やす
> - **重い商品から順に詰める**
> - **各口の申告額は、その口に入っている商品の合計金額**（全体を均等に割ってはいません）
>
> **実際の分け方が違えば、関税・消費税も変わります。**

補足が要る場面向けの長い版:

> **箱を何個に分けるか、どの商品をどの箱に入れるかは代行会社が決めます。** これは梱包の
> 時点で初めて決まることで、私たちには知りようがありません。そこで、次の前提を置いて
> 仮に計算しています。
>
> - 配送方式ごとの重量・寸法の上限を超えたら箱を増やす
> - **重い商品から順に詰める**（実際にどの商品がどの箱に入るかは代行会社次第です）
> - **各口の申告額は、その口に入っている商品の合計金額**です（全体を均等に割ってはいません）
>
> **実際の分け方が私たちの前提と違えば、関税・消費税も変わります。** 各口は届け先国の
> 免税しきい値に対して別々に判定されるため、分け方によって合計の関税・消費税が
> **高くなることも、低くなることもあります。** たとえば1箱にまとめれば免税枠を超えて
> 課税される場合でも、複数口に分かれることで各口がしきい値未満になり、合計では
> 課税されずに済むことがあります。逆に、まとめれば免税枠に収まる注文が、分かれ方次第で
> 一部の口がしきい値を超えて課税されることもあります。どちらに転ぶかは代行会社の
> 実際の詰め方次第で、私たちの前提だけでは決め切れません。
