# 箱の大きさの手がかり調査（公開ページ）— 2026-09-12

## 目的

`master/fees.json` のコードは箱を **20×15×10cm 固定**（測定条件を揃えるための基準箱であり、現実のカートの箱ではない）で扱っている。実請求データで寸法が分かるのは1件（7点・梱包後3,210g・42×31×24cm）のみで、1件では中央値も分布も分からない。

代行は利用者の商品を梱包して送るため、**箱を決めるのは代行側**である。そこで、各社の公開ページ（ヘルプセンター・FAQ・ブログ）に「商品 → 箱の大きさ」を推し量れる情報（梱包例・箱サイズ一覧・梱包後寸法の目安・送料計算例・保護梱包オプションの説明）がないかを調べた。**調査のみで、コード（`src/`）とマスタ（`master/`）、`docs/ROADMAP.md` には一切触れていない。**

すべての確認は 2026-09-12（本日）に実施。取得経路は WebFetch と WebSearch のみ。アカウント作成・ログインは行っていない。CAPTCHA には遭遇しなかった。

## 前提として読んだ既存の監査文書

- `docs/audit/o2-courier-webfetch-2026-09-11.md` — WebFetch でも ZenMarket・FROM JAPAN 本体ドメイン・Buyee は403で遮断されることが多いという記録。
- `docs/audit/declared-value-2026-09-12.md`（タスク指示にあった `declared-value-basis-2026-09-12.md` という名前のファイルは存在しなかったため、同日付の近い監査文書としてこちらを参照した）— Buyee・Neokyo(zendesk)・ZenMarket は直接 fetch が403になりやすく、Jauce (`jauce.com`) と FROM JAPAN のブログサブドメインは直接取得できた、という記録。

**今回の実測はこの記録と概ね一致した**が、タスク指示にあった「到達できている」という前提の一部（`neokyohelp.zendesk.com` の記事HTML直接取得、`zenmarket.jp/en/blog` と `.../shipping.aspx`）は、**今回は403で到達できなかった**。詳細は社ごとの結果を参照。

## robots.txt の扱い

- `neokyo.com` の `Disallow: /*?*` は `neokyo.com` 自体のパスに適用されるものと解釈し、別ドメインの `neokyohelp.zendesk.com`（Zendesk公式API含む）へのアクセスには適用していない。**この判断はタスク指示の「Zendesk の API は別ドメインなので可」という記載に基づく。**
- `jauce.com` はクエリ文字列付きURL（`?article=22` 等）へのアクセスを行った。`o2-courier-webfetch-2026-09-11.md` の記録によれば `jauce.com/robots.txt` には admin/images系以外の制限がなく、クエリ文字列の禁止規定も記録されていないため、問題ないと判断した。**ただし今回のセッションでは `jauce.com/robots.txt` を自分では再確認していない**（既存記録への依拠であり、弱点として記す）。
- ZenMarket・FROM JAPAN本体・Buyeeへのアクセスは全て403で止まっており、robots.txtの許可・不許可以前にサーバー側で遮断されている。

## 箱の大きさについて何が言えるか

**言えることは非常に限定的である。**

1. **「商品→箱の大きさ」を直接示す情報は、今回到達できた範囲では見つからなかった。** 写真つきの梱包例、箱サイズの一覧（S/M/L等の区分）、梱包後寸法の目安（「+◯cm」等）は、Neokyo・Jauce の到達できた記事の中にはなかった。
2. **FROM JAPAN と ZenMarket には、まさに求めている情報が載っていそうなページの存在自体は分かった**（FROM JAPANの「Storage, Packing and Shipping」、ZenMarketの「Tips for Creating a ZenMarket Parcel」）。**しかし両方とも本体ページには到達できず、内容を確認できていない。** WebSearchのスニペット経由でFROM JAPANのページについて「コンパクトに梱包しシュリンクラップで小型化する」「壊れ物は追加の緩衝材・厚紙で包む」という記述があるらしいことは分かったが、**具体的な寸法の数値は含まれておらず、要約経由の情報である**ため、箱サイズの根拠にはできない。
3. **Jauceで見つかったのは、代行の梱包方針ではなく、配送業者（Japan Post）が受け付ける上限寸法**（30kg以下、長さ+胴回り合計275cm以下、最大長150cm以下）である。これは「箱の上限」の参考にはなるが、「通常の商品がどの大きさの箱に収まるか」という分布や目安を示すものではない。
4. **Buyeeは今回も一切到達できず、情報の有無すら判断できない。**
5. **したがって、「代行の公開ページから箱の大きさの中央値・分布・目安を導く」ことは、今回の調査結果からはできない。** 到達できなかった2つのページ(FROM JAPAN・ZenMarket)に有用な情報がある可能性は残っているが、**それを裏付けることも否定することもできていない。**

**結論として、次に取るべき手段はタスク指示にある通りP6（実請求データを増やす）である**と、今回の調査結果は支持する。公開ページからの手がかりは、現時点では「存在するかもしれないが確認できないページが2つある」という状態にとどまり、コード・マスタに反映できる数値的根拠は得られなかった。

## 自分の調査の弱点

- **最も価値が高いはずの2ページ（FROM JAPANの「Storage, Packing and Shipping」、ZenMarketの「Tips for Creating a ZenMarket Parcel」）に、結局到達できなかった。** これらのタイトルからは本調査が最も求めている情報（梱包例・箱サイズ）が載っている可能性が高く、**調査の核心部分が未完である。** WebSearchのスニペットだけでは、寸法などの具体的な数値までは拾えなかった。
- **403の原因を切り分けていない。** Cloudflare/WAFなのか、ボット判定なのか、リクエスト頻度の問題なのかを区別しておらず、時間を空けた再試行、User-Agentの違い、Wayback Machine経由での取得可能性などは検討していない（本タスクのスコープをWebFetch/WebSearchに限定したため）。
- **タスク指示にあった「到達できている」という前提の一部が、今回のセッションでは再現しなかった。** Zendeskの記事HTML直接取得、`zenmarket.jp/en/blog`、`zenmarket.jp/en/shipping.aspx` は、指示文書では到達実績ありとされていたが、今回はすべて403だった。到達可否がセッション・時間帯によって変動する可能性があり、**「到達できない」という結論も恒久的なものではなく、今回時点の記録に過ぎない。**
- **Neokyoの記事20件のうち、本文まで確認したのは7件のみ。** 残り13件（通関書類・関税コード・返金・Discord案内など、タイトルからは無関係と判断したもの)は確認していない。タイトルだけでは判断を誤っている可能性がある。
- **Jauceのカテゴリのうち、Shipments & Handling以外（Tutorial / Auctions / Payments / Shopping）の記事本文は確認していない。** タイトルからは梱包に無関係と判断したが、これも本文未確認のままの判断である。
- **WebFetchは「HTML→Markdown変換→小型モデルによる要約」を経由する**（`o2-courier-webfetch-2026-09-11.md` が既に指摘した限界と同じ）。本監査でも、Zendesk API記事の本文や、Jauceの記事について「逐語引用」として記録した部分以外は要約であり、**原文の完全性は保証されていない。**
- **写真つきの梱包例は、到達できたページの中には一件も見つからなかった。** これはタスクが最も価値が高いとした情報であり、**今回の調査では得られていない。**
- **`jauce.com/robots.txt` を今回のセッションで自分では再確認せず、過去の監査文書の記録に依拠した。**
