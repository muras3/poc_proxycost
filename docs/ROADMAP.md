### 2026-09-12 に確定した決定（今後蒸し返さない）

1. **燃油サーチャージは各代行の宅配便表示額に「込み」として扱う**——一般的業界慣行からの
   推論であり一次確認された事実ではない、と `master/carrier-surcharges.json` に明記した
   （`conclusions.fuel_surcharge_working_treatment`）。境界検証（2026-09-19/20 vs 09-22/23）は
   引き続き未実施。**計算は何も足さない**——これは変更前と同じ挙動であり、今週の表示額は変わらない。
2. **宛先側の非公表手数料は区間の上端に乗せる。**「¥X 以上（上限不明）」という表示になり得る。
   順位は下端（下限）で決める。
3. **既定の配送方式は、船便を除く現条件での最安**（条件ごとに再計算）に変える。船便は
   2〜3か月かかるため既定から外すが、消えるわけではなく、代行自身の行の中に価格と到着目安
   つきのフィールドとして残す（5社比較で1社が2行になるのを避けるため、別行にはしない）。
   日本郵便自身の船便方式も既定から除外する。**これは実請求の言及数（FedEx 12 / EMS 11 /
   UPS 7 / DHL 7 / 船便 3 / 航空便 1）から選ばれていた旧既定 `'ems'` を置き換える**決定——
   旧根拠が存在したことと、それが上書きされたことの両方を記録として残す。
4. **運送会社のティア（等級）はそれぞれ別の method id を持つ**（1社1枠にまとめない）。理由は
   3つ: (a) 公開されている社ごとのラインナップをそのまま鏡写しにするのが筋、(b) ティア間で
   順位が入れ替わる（ZenMarket の FEDEX と FEDEX LOWCOST は 5000/10000/20000g の間で2回
   順位が入れ替わる）、(c) 到着目安が違う（FedEx Economy 5〜7日 vs Priority 2〜3日）。
5. **実測点の間の重量は補間せず区間で持つ**（`[p(w₁), p(w₂)]`）。実測済み4社すべての方式が
   ドイツの11点重量カーブで単調増加と確認できているため成立する前提——今後の取り込みが
   単調性を破ったら CI が落ちるようテストを追加する作業が進行中。
6. **未計測の国はその宅配便を「理由つきで欠落」のまま扱う**（¥0にしない・他国の値を
   流用しない）——料金帯の境界が社・方式ごとに違うため。

### 確定仕様（全5点、2026-09-11）

1. **総額は `{low, high}` の区間。**`Line.amount` を **点 / 区間 / 未取得（理由つき）** の3状態にする（1a〜1c と同じ）
2. **順位は下端で並べる。**「おすすめ」の枠は**1位を含めて最大2社**。1位の幅と重なる社があれば、そのうち1社までを枠に足す。重なる社が無ければ単独1位。**枠に入りきらない重なる社（2社目より後ろ）には「同等」の印**を付ける（枠には入れない）
3. **差額は下端差で出す。**「少なくともいくら得か」という言い方をする。上端差は使わない
4. **上端は「額 × 期間」で置く。**期間（回数・日数）が公表されていて閉じてさえいれば、**単価が未公表でも上端が出せる。**
   例: Jauce の保管料は月額が未公表だが、**無料60日・最大保管120日**なので有料期間は最大2か月に閉じている。
   公表されている参考額（¥200〜¥700/月）と掛け合わせれば根拠のある上端が出る（`master/fees.json` F20/F21 jauce）。
   同じ形が Neokyo の "up to a limit of six unpaid weeks"、Buyee の "Maximum storage period is 90 days" にもある。
   **「額×期間」のうち期間さえ閉じていれば、額の桁が未公表でも上端は置ける**というのが一般則
5. **上端が置けない費目は「上限不明」として別表示する。**総額は「¥43,940 以上（3件は上限不明）」のような形にする。
   **おすすめ枠の判定は下端のみで比較する**（上限不明の行があっても下端の比較には影響しない）

**「上端に入れない」を選んだ理由**: 該当社をおすすめ枠の判定から外す案もあったが、
**その社の調査量の差（＝この3費目のうち何個を抱えているか）を不利として画面に出す**ことになり、
「マスタに無い＝発生しない、ではない」というリポジトリの原則の逆になる。
該当は3件だけなので、画面はほとんど汚れない。

### 既存3判定との整合

- **`comparable`** ── 上限不明の行がある比較でも `comparable` のまま。上限不明を理由に比較対象から外さない
- **`rankStable`** ── 判定基準を「1位が入れ替わるか」から「**おすすめ枠（上の #2）が変わるか**」に変える。
  **枠の中での入れ替わりは「動いた」と数えない**
- **`weightSensitivity`** ── 同じ基準に変える

**`rankStable` の判定方法が変わるので、README にある「既定重量では7カ国すべて `rankStable=false`」という
記述はそのままでは通らない可能性がある。実装時に新しい判定基準で測り直し、README を更新すること。**
**いまこの数字を書き換えてはいけない（まだ実装していない）。**

### 全社が重なったときの表示（オーナー判断 2026-09-11）

```
┌────────────────────────────────────────────┐
│ この5社は、差が不確かさの中に収まっています     │
│ どこを選んでも総額はほぼ変わりません           │
│                                            │
│ 最安を狙える可能性が最も高い: Neokyo         │
│                                            │
│ → 総額に効くのは配送方法です                 │
└────────────────────────────────────────────┘
```

- **「どこを選んでも大差ない」と明言する**
- **下端で並べた1位は出す。**ただし「最安」ではなく「**最安を狙える可能性が最も高い**」という書き方
- **配送方法の選択へ誘導する**

**根拠**: 配送方法による差は**2.3倍**（スペインの同一荷物で船便€27〜EMS€63、差€36≒¥5,900）で、
**会社間の最大差（5点で¥5,250）を上回る。**会社が区別できない状態は欠陥ではなく、
**本来見るべき軸（方法）に目を向けさせる正しいタイミング。**

**実カートでこの状態が起きることを確認済み**（P1-2 実装、既定5点・¥3,000・600g・ヤフオク・米国）:
FROM JAPAN・ZenMarket がおすすめ枠（枠は1位を含めて最大2社）、Buyee(consolidated)・Jauce・
Buyee(default) が「同等」の印で、**比較可能な5社全員がおすすめ枠か同等のどちらかに収まっている。**
この状態は「安定」ではなく「判定不能」（下の判断3）——米国はこの表示と `rankIndeterminate` の
両方の実例として使える（**このP1-2ではUIを作らない**——P1-3で実装する。この節は仕様として
先に書いておく）。

### P1-2 実装で確定した3つの判断（コーディネーター、2026-09-11）

**論点**: `high === null`（上限不明）の行を「重なる」の判定でどう扱うか。実装過程で、
それを候補行の下端が1位の下端に近いかで代用する案と、+Infinity として扱う案があった。
+Infinity 案を最初に実装したところ、**1位自身が上限不明のときに全社が自動的に重なり、
`rankStable` が7カ国全部で `true` になる**という副作用が実測で見つかった
（`rankStable` が「枠の誰か1人が両端で生き残るか」という初期の判定基準だったため、
枠が3社に膨らむとほぼ自明に「誰か残る」が成立してしまっていた）。

**判断1（重なり判定は変えない）**: `high === null` は **+Infinity として扱うことを維持する。**
上限不明は「上端が無い」のではなく「差が不確かさに埋もれている最も強い状態」であり、
これを有限に丸めたり判定から除いたりすると、**不確かさを隠して差が分かるふりをする**
ことになる——このプロダクトが最も避けるべき欠陥。「枠が全社を飲み込む」という懸念は、
**枠に最大2社という上限（確定仕様2）がある時点で成立しない。**2社目より後ろは枠に入らず
「同等」の印だけが付く。

**判断2（壊れていたのは `rankStable` の定義）**: `rankStable` を
**「おすすめ枠の集合が ×⅓・×3 の両端で基準と完全に一致するか」**に変える。
**集合の一致であって、「枠の誰か1人が両端で生き残るか」ではない。**
枠の中で誰が下端最小かの入れ替わり（順序）は見ない——`Set` として比較するので
内部の並びは無視される——が、**枠に出入りする社が1社でもあれば `false`。**
枠は最大2社なので、「誰か1人残ればよい」という基準は5社中2社が枠に入る局面でも
十分高い確率で成立してしまい（2社のうち片方さえ残ればよい）、判定として機能しない。
`weightSensitivity.decisive` も同じ規則に変える。

**実装バグの訂正（コーディネーター指摘、2026-09-11）**: 判断1・2を最初に実装したとき、
`computeBracket` が「1位＋重なる社2社まで＝最大3社」を作っていた。**確定仕様2は
「1位を含めて最大2社」**（オーナーの言葉「おすすめは上位**二つ**まで」「**二つとも**
囲って」）で、3社ではない。枠が3社まで膨らんでいたことは判断2で直した
「誰か1人残ればよい」基準の再発防止をさらに弱めていた（3社中1社より2社中1社の
ほうが「誰か残る」確率は低いが、それでも十分ではないことが下の判断3で分かった）。
修正し、枠が2社を超えないことをテストで縛った。

**判断3（「安定」と「判定不能」を分ける）**: 判断2で「枠が広いと『誰か1人残る』が
自明に成立して機能しない」問題を潰したはずが、**別の入口から同じ形の自己欺瞞が
戻ってきた。**1位の総額が上限不明（`high === null`）だと、+Infinity 扱い（判断1）に
より下端で並ぶ**比較可能な全社**が1位の区間と重なりうる——枠2社・残りは同等という
上限はあっても、**全社が枠か同等のどちらかに収まってしまう**ことがある。この状態は
重量を動かしても「全員が重なっている」という前提そのものが変わらないので、
判断2の「枠の集合が変わるか」は機械的に `true`（安定）を返す。だが実態は
「重量が変わっても薦める社が変わらない」という意味の安定ではなく、**「そもそも
どの社が安いか一切判別できていない」。**`rankStable: boolean` だけではこの2つが
同じ `true` に潰れる。

**対応**: `CompareResult` に `rankIndeterminate: boolean` を追加した。比較可能な
全社がおすすめ枠か同等の印に収まっているとき `rankIndeterminate = true` とし、
**このとき `rankStable` は必ず `false`**（`rankIndeterminate` を「安定」側へ絶対に
寄せない）。`rankStabilityNote` もこの状態専用の文言（「これらの社は差が不確かさの
中に収まっていて、どの社が安いか区別できない。総額に効くのは配送方法」の趣旨）を
返す。`measured.ts` の `RankStabilityRow` にも同じフィールドを足し、README の表に
「安定 / 不安定（重量で変わる） / 判定不能（全社が不確かさの中）」の3状態を出す。

この3つの判断を反映した結果、既定カート（5点・¥3,000・600g・ヤフオク）の7カ国は
`rankStable` が AU/SG=`true`、GB/DE/FR/CA=`false`（不安定）、US=`false`
（`rankIndeterminate=true`、判定不能）となった。P1-1 時点の値（US/AU/SG=`true`）
から **US が「安定」→「判定不能」に変わった**——これは判断3の意図どおりの変化であり、
`measured.ts` の `RANK_STABILITY` を更新し `render-docs.py` で README を再生成した。
「7カ国すべて true」という壊れた判定も、「枠が3社に膨らむ」バグも再発しないことを
テストで縛った（`src/lib/pricing/compare.test.ts` の `rankStable is judged on the
recommended bracket as a set` 節、および枠の上限2社を縛る節）。

### P1-4 ──「判別不能」が全社を飲み込んでいた欠陥（外部レビュー、オーナー確定 2026-09-11）

**何が起きていたか**: UI の実際の既定カート（Miku ¥12,800 ヤフオク＋Nendoroid ¥4,200
メルカリ、重量表・EMS・45日）で、7カ国中6カ国（US を除く GB/DE/FR/CA/SG、および
当時 AU も一部条件で）が `rankIndeterminate: true` になり、「これらの社は同じ
不確かさの中にあり、どれが勝つか分からない」と画面に出ていた。**しかし実際には、
上限が確定している社同士で明確な差があった**（例: GB の Neokyo `[35,921..35,921]`
と Buyee default `[44,982..44,982]` は確定差 ¥9,061）。利用者がこの表示を信じて
高い方を選べば実際に損をする——実害のある欠陥だった。

**原因**: P1-2 の判断1「`high === null` は +Infinity として扱う」自体は誤りではない
（上で述べたとおり維持する）。誤っていたのは、その先の推論——「枠は最大2社だから
全社を飲み込むことはない」。`computeBracket` で1位（下端最小の社）の `total.high`
が `null` だと `leaderHigh = Infinity` になり、**枠に入りきらなかった行はすべて
無条件で `equivalent = true` になっていた。`equivalent` には枠のような上限が無い。**
`isIndeterminate` は「比較可能な全社が `recommended || equivalent`」で判定していた
ため、枠の定員（2社）を迂回して全社が「判別不能」に巻き込まれていた。
FROM JAPAN は外注梱包費（`unpricedFees`）が常に上限不明なので、FROM JAPAN が
下端1位になるだけでこの経路が開いた。

**直した内容（2箇所、両方が要る）**:

1. **`computeBracket`**: 枠・同等の判定に使う境界（`bound`）を、**既知の上限
   （`high !== null`）を持つ行を通すたびにしか伸ばさない**ようにした。上限不明の
   行を枠や同等に入れることは引き続き認めるが、その行の「上限が分からない」という
   事実を、以降の他社の重なり判定に持ち込まない——1位グループが全員 `high === null`
   のときだけ、境界は最後まで `null`（実務上 Infinity 相当のフォールバック）のまま
   残る。
2. **`isIndeterminate`**: 「比較可能な全社が枠か同等に収まっているか」という
   **派生した印**を見るのをやめ、「**比較可能な全社の上端が置けない
   （`total.high === null`）か**」という**一次の事実**を直接見るようにした。
   `computeBracket`／`overlapsLeader` は上限不明の1位を +Infinity として扱う経路を
   引き続き持つ（判断1は維持する）ので、`recommended`／`equivalent` だけを見て
   判定不能を測ると①のような巻き込みが再発しうる構造は残る。**閉区間同士に確定した
   差がある限り、それは判定不能ではない**という事実を、派生した印を経由せずに
   `total.high` から直接測ることで、巻き込みの経路そのものを断った。

**なぜこの2つで足りるか（4条件をテストで縛った）**:

1. **US（全行が `high === null`）は `rankIndeterminate: true` のまま**——`isIndeterminate`
   の新定義がそのまま真になる（`comparable.every(r => r.total.high == null)`）
2. **GB/DE/FR/CA/SG（既定カート）は `rankIndeterminate: false` になる**——実測で確認
   （下表）
3. **閉区間同士で差が付いている2社が、同時に「同等」にならない**——`computeBracket`
   の境界が既知の上限からしか伸びなくなったので、2社の間に閉じた実際の差がある限り
   境界がそこで止まる
4. **上限不明の行を順位や比較から除外しない**——`comparable` の判定にも
   `computeBracket`／`rank()` の対象にも一切手を入れていない。上限不明の行自身の
   「他社より高いかもしれない」という不確かさ（`recommended`／`equivalent` の対象に
   なるかどうか）は判断1のまま変えていない。変えたのは「判定不能」という**要約の
   文言を出す条件**だけ

**実測（UI の既定カート、EMS・45日）**:

| 国 | 修正前 `rankIndeterminate` | 修正後 |
|---|---|---|
| US | true | true（全行 `high === null`。設計どおり） |
| GB | true | false |
| DE | true | false |
| FR | true | false |
| CA | true | false |
| SG | true | false |
| AU | false | false（変化なし。1位が閉区間の Neokyo で、そもそも巻き込まれていなかった） |

**止めなかった理由**: 4条件を同時に満たす定義が作れないケースも、`rankStable`／
`RANK_STABILITY` が動くケースも無かった（`measured.ts` の基準カートは 600 g・
US 以外で元々 `rankIndeterminate: false` だったため無変化。`measured.test.ts` で確認
済み）。

### P1-4 追記 ──「全社共通の未知」が米国の順位判定そのものを殺していた（外部レビュー、オーナー確定 2026-09-11）

**①の修正後も米国だけは `rankIndeterminate: true` のままだった。**当初これを
「全行の上端が置けないので正しい」と説明したが、**プロダクトとして誤りだった。**

**何が起きていたか**: 米国で上端が置けない費目を実際に見ると、ZenMarket・Buyee・
Jauce の3社（FROM JAPAN 以外）は `Sales tax / VAT`（連邦売上税が無いこと）と
`US import prepayment (Zonos) fee`（前払い利用料。額が非公表）の2件だけが未取得で、
どちらも**輸入側（買主側）でかかるもので、どの社を使っても同じようにかかる。**
FROM JAPAN だけがそれに加えて `Outsourced packing`（外注梱包。社固有・偶発的）を
持つ。つまり米国で本当に分からないのは**総額の絶対値**であって、**どの社が安いか
ではない**——Zonos・連邦売上税は全社の総額を同じだけ押し上げるだけで、社同士の
差には一切効かない。だが `isIndeterminate`（P1-4 の①修正版）は `total.high` を
そのまま見ていたので、この「差を生まない共通の未知」のせいで比較可能な全社の
`total.high` が `null` になり、**最大の市場である米国だけ、閉区間同士の確定した
差があっても「どこを選んでも総額はほぼ変わりません」としか出せなかった。**

**直した内容:** 未取得の費目を2種類に分けた。

1. **共通の未知**（`Line.scope === 'shared'`）── 比較可能な全社に同じようにかかる
   もの。**輸入側の判定だけを行う `taxLines()` がこの行を作るときにだけ**
   `'shared'` を付ける——`taxLines()` は国・カート（品目・価格・重量）だけで
   決まり、**社の識別子を一切見ない関数**なので、そこが作る null 行は構造的に
   「差を生まない」と言える。対象は現状4行: 米国の `vat`（連邦売上税が無いこと）・
   `duty-prepayment`（Zonos）・`duty`（税率非公表、条件が立てば）・`excise`
   （英国の酒税、ABV 不明で額を出せない場合）。
2. **社固有の未知**（`scope` 無し、既定）── その社だけにかかるもの
   （FROM JAPAN の外注梱包・`prepaid-import-tax` の「確認できていない社」など）。
   従来どおり、その社の順位を不確かにする。

**判定方法の根拠**: マスタ（`master/fees.json`）の `kind: country_side`
（F31〜F34・F38）はこの区別に近いが、F35（Zonos 相当）に付いていない・
`taxLines()` の行と1対1に対応しないため、そのままは使えなかった。代わりに
**「どの関数がその行を作るか」という構造的な事実**で判定した——`taxLines()`
はシグネチャに社の識別子を持たず、国・カート情報だけで呼ばれる。これは
「実際の行を見て、たまたま全社に出ているかどうかで判定する」方式（コーディネーター
が懸念した「社固有の費目をたまたま全社に出ているからと誤って共通と見なす」危険）
とは違う——**費目がどの関数から来たかという出自**で判定するので、たまたま今の
カートで全社に出ているかどうかに左右されない。`services.ts` の `unpricedFees`
（社ごとの catalog）から来る行は、たとえ将来複数社に同じキーが現れても
`scope: 'shared'` を明示的に付けない限り社固有のまま扱われる。

**具体的な実装**:
- `Line.scope?: 'shared'` を型に追加（`src/lib/pricing/types.ts`）。`L()` ヘルパー
  に7番目の引数として追加し、`taxLines()` 内の4つの null 分岐にだけ付けた。
- `Row.rankHigh: number | null` を追加——画面には出ない内部専用の上端。
  `rankHighFor(lines)`（`totalRange()` とほぼ同じだが `scope === 'shared'` な
  null 行を 0 として畳む）で `buildRow()` が計算する。
- `computeBracket`／`isIndeterminate` は `total.high` の代わりに `rankHigh` を見る
  よう変更。**`total.high`（画面表示）は一切変えていない**——共通の未知がある
  かぎり「以上（上限不明）」の表示はそのまま残る。

**なぜ両立するか（①を壊さない理由）**: ①の修正（境界は既知の上限を持つ行からのみ
伸ばす）と④の修正（共通の未知を無視する）は直交する。①は「1件の上限不明が

### `claude/courier-model` PR で入れた器（2026-09-11）

**方針（オーナー確定 2026-09-11）: 宅配便は「最終価格」を正とする。分解しない。**
各社は FedEx 等と法人契約しており、割引・重量帯別契約・燃油・住宅地サーチャージ・
自社マージンが外から分離できない。「定価 × 上乗せ率」を逆算すると根拠のない構造を
発明することになるので、日本郵便のような「公表額＋上乗せ」（`markup`）の形は使わず、
帯（重量・容積重量）ごとの最終価格をそのまま持つ `measured` を新設した。
`FROM JAPAN × FedEx Economy = ¥5,309`（DE, 600g）を正として持てる形にする——
公式が「送料／手数料」を分けて表示している場合だけ、呼び出し側で別項目にする
（データそのものは分けない）。**日本郵便の `markup` の仕組みには一切手を入れていない。**

- `services.ts`: `PostageRate` を判別可能合併にした。

### 容積重量の除数「5000」は仮説であって確定値ではない（外部調査、2026-09-11 取り込み。2026-09-12、Buyeeについては決着）

**2026-09-12追記: この節の見出しはBuyeeに関しては、もはや「仮説」ではない。**PR #79 が
Buyee自身の画面表示（容積重量、668行で÷5000と例外なく一致）から除数5000を確定させた

入手できていた情報（外部調査・当時汚染されていたBuyeeの実測）に基づく記録として、当時の
文面のまま残す**——読者が以前この節を読んで「Buyeeは5000に従わない」と記憶している場合に、
その主張が今どうなったかを追えるようにするため。FROM JAPAN・ZenMarket以外の社・方式に
ついては、なお個別の実測裏付けが無いままである点は変わらない。

外部調査（GPT）は「FedEx・UPS・DHL は公式に除数 5000」と書いているが、**これを
確定値として `MeasuredPostageRate.volumetricDivisorCm3PerKg` の既定値にはしない

実測から決める」のままであることを本PRで確認済み）。**理由:

  この違いを前提にしている）
- **外部調査自身も後段で「Rate() は契約料金の段階表になっている可能性が高い」
  「綺麗な数式を無理に探す必要はない」と書いており、下の実測結論と一致する**

  ZenMarket の実効除数を UPS ≈9.5 / Nova ≈11.9 と算出しており（測り方が
  `blank`＝既定の箱混入で汚染されていた可能性込み。同 §3 参照）、**5000 でも
  6000 でもない**

したがって **5000 は「最初に検証すべき仮説」**であって確定値ではない ──
実測（上の入力マトリクス、特に §5 が指定した UPS・DE・compact 断面）が 5000 と
一致すればそれで確定、しなければ実測が正という順序を崩さない。

### assumption 5 の置き場所について

これまで Air Waybill 数の数え方（shop-based split ⇒ 別々のAir Waybill、重量上限での分割 ⇒
同一Air Waybillのmulti-piece）は、`master/carrier-surcharges.json` の C13
（`zero_duty_clearance_fee_working_treatment`）の `cross_reference` フィールドに埋め込みで
しか言及されていなかった。C13はサーチャージの working treatment を記録するエントリで、
Air Waybill数それ自体はサーチャージではなく通関手数料の課金単位（#4）に付随する事実であり、
本来の置き場所は `master/customs.json` 側だった。

本PRで、Air Waybill＝Shipmentの単位定義が既に記録されている `master/customs.json` の
FedEx GB/DE の `unit_note`（`clearance[].fee_structure` 配下）に、shop-based splitとの
対応関係を明記する注記を追加し、`master/carrier-surcharges.json` のC13からはこの注記への
相互参照を残した。**C11/C12/C13の相互参照網（`cross_reference`フィールド）自体は変更していない**
――追加のみで、既存の参照は保っている。

### 8件目（按分）について

このタスクの依頼時点の想定は「暫定的な仮定は7件」だったが、検証の過程で追加候補が
1件見つかった: `master/fees.json` の `F39c`（複数個口への申告額の按分方法）は、
5社いずれも按分方法自体を公式には明言していないと記録されている一方、
`src/lib/pricing/parcels.ts` は具体的な按分ロジック（`packHeaviestFirst()` 等）を実装して
動いている。つまり「実装済みの按分規則」と「その規則が代行5社の実際の運用と一致するという
一次資料での確認」は別軸であり、後者は未確認のまま本番で使われている。**#121が独立に
同じ論点を「8件目」として数えていることを確認した**ため、上の表では暫定7件ではなく
8件として掲載した。それ以外に、`src/lib/pricing/` および `master/` を横断して探した範囲
では、この8件のほかに一次資料が決着しないまま本番で使われている仮定は見つからなかった。
