# proxycost — 総額精度の検証計画

対象：Buyee / ZenMarket / Neokyo / FROM JAPAN / Jauce ／ 7カ国
作成 2026-09-07。前提の確認は本リポジトリ HEAD（`src/calc.js` / `src/data.js`）に対して実施した。

---

## 0. 先に結論

1. **「各国で総額を実額に限りなく近づける」の全数実購入検証は、この規模のプロジェクトでは実行できない。**
   proxycost 自身の見積で米国宛15件＝**約 ¥220,000**（§5、実測）。7カ国に広げれば約 ¥150万、
   盲検100件で約 ¥147万。収益目標は AdSense で月 $60（`REQUIREMENTS.md` §5）。
   **検証費が製品の生涯収益を上回る。**計画をそのまま実行することが最大のリスク。

2. **代わりに誤差を独立な3源に分解し、源ごとに別々に測る。**
   実購入が要るのは3源のうち1つ（輸入時の税・通関）だけ。残り2つは購入0件で測れる（§1〜§3）。

3. **最優先の検証は総額精度ではない。**
   現在の順位は `src/data.js:37` の `domesticIncluded: true`
   （Neokyo の ¥350 に国内送料が含まれるという仮定）という**未検証の bool 1個**が決めている。
   `docs/DESIGN-NOTES.md` §1 が挙げる唯一の順位逆転条件がこれと同じ構造
   （国内送料が0になると1位が Neokyo → FROM JAPAN に入れ替わる）。
   ここが外れていれば、総額の精度を何%改善しても製品の唯一の約束（順位）が崩れる。
   **これは1件の実購入で決着する。15件より先に、これを単独でやる。**

4. **計画案の合格基準は統計的に成立しない。**
   - 「各社3件のうち2件以上が±10%」→ 2/3合格の真の合格率 95%下限は **13.5%**。
     真の精度が13.5%しかなくてもこの基準は通る。事実上の無検定。
   - 「15件の誤差率中央値8%以下」→ n=15 の中央値の95%CIは**4番目〜12番目の順位統計量**、
     つまり分布のほぼ全域。中央値には合否を判定できるだけの分解能が無い。
   - 「15%超の過小予測が0件」→ 15件で0件でも、真の失敗率は**最大18.1%**まで許容される（rule of three）。
   - 「±10%以内が80%以上」を95%信頼で言うには、**全件合格でも n≥14**、
     現実的な合格率85%なら **n≈150** が要る。
   → **n=15 は合否判定ではなく「符号の大きい欠陥を見つける探索」。合格基準を書いてはいけない。**

5. **点予測ではなく区間で評価する（§7）。**
   米国は de minimis 停止・HTS依存の関税率・配送業者のブローカー手数料で、
   予測時点に点予測を出せる構造になっていない。区間とカバレッジで評価すれば正直に出荷できる。

## 1. 誤差の分解

```
実額 = 商品代 + 国内送料 + 代行手数料 + 入金/決済手数料 + 梱包料
       + 国際送料 + 輸入時の税・通関費 + 為替差
```

| 費目 | 予測時点で確定するか | 誤差源 | 測り方 | 実購入 |
|---|---|---|---|---|
| 商品代 | する（入力値） | なし | — | 不要 |
| 代行手数料 | する（料金表引き） | 表の転記ミス・改定漏れ | 単体テスト＋請求書1件 | 各社1件 |
| 入金/決済手数料 | 支払方法が分かればする | 支払方法別レートの未取得 | 請求書 | 各社1件 |
| 梱包料 | 梱包後重量に依存 | 源#2に従属 | L2 | 不要 |
| 国内送料 | **しない** | **源#1** | L2/L3 | 少数 |
| 国際送料 | 重量とゾーンの関数 | 表の誤り＋**源#2（梱包後重量）** | 表→L1、重量→L2 | 不要 |
| 輸入時の税・通関 | **しない** | **源#3（国依存・閾値で不連続）** | L3/L4 | **必須・国ごと** |
| 為替差 | **しない** | 利用者のカード発行会社の上乗せ（実勢 1.5〜3%） | 判定通貨を円にして分離 | — |

**独立な誤差源は3つだけ。**
- **源#1 国内送料**：出品ページの送料表示と、代行が実際に使う配送方法が一致しない。
  現行は `ASSUMED_DOMESTIC_SHIPPING = 800`（`src/data.js:70`、実勢 ¥150〜1,500 の中の一点仮定）。
- **源#2 梱包後重量・容積**：国際送料は総額の最大項目で、その入力が最も弱い。
  現行は `PACKING_MULTIPLIER = 1.2` / `PACKING_ADD_G = 300`（同 71-72行、いずれも仮定と明記）。
- **源#3 輸入時の税・通関**：国・郵便番号・HTSコード・申告額・配送業者・DDU/DDP に依存し、
  閾値で不連続。**唯一、国ごとに実データを要する。**

**為替は proxycost の管轄外。**カード発行会社の上乗せは利用者ごとに違う。
これを含めて誤差を測ると、測っているのは利用者の銀行であってモデルではない。
→ **モデルの合否は円で判定し、請求通貨での差は「FX帯」として別掲する。**

## 2. なぜ分解しないと駄目か

15件の end-to-end 試験は、**3つの独立誤差の和を15サンプル観測するだけ**。
誤差率12%という結果が出ても、重量が悪いのか国内送料が悪いのか関税が悪いのか分離できない。
そして分解すると、源ごとに必要サンプル数も取得コストも桁で違うことが使える：

| 源 | 必要サンプル | 取得手段 | 1サンプルの費用 |
|---|---|---|---|
| 料金表（源#0） | 各社1〜2 | 公式ページ＋請求書 | ¥0〜7,000 |
| 源#1 国内送料 | 20〜30 | 実注文の第2回請求 | ¥0（他の試験に相乗り） |
| 源#2 梱包後重量 | 30〜50 | **倉庫到着時の実測値**（配達前に取れる） | ¥0（相乗り） |
| 源#3 税・通関 | **国ごと** 20〜30 | 配達完了の請求 or 他人の請求書 | ¥8,000〜15,000 |

源#1・源#2 は**同じ注文から追加費用ゼロで取れる**。
費用がかかるのは源#3 だけで、しかも国ごとに必要。ここが計画のボトルネック。

## 3. 5層のテスト

### L0 — 計算の単体テスト（実購入0件・即日）

**現状 0 件。**`package.json` は `node --test 'test/**/*.test.js'` を実行するが `test/` が存在せず、
`npm test` は `1..0` を返して成功扱いになる（README の「test/calc.test.js 7件」は事実と異なる）。
ここが空のまま実購入を始めるのは順序が逆。

- EMS 全27段の境界（`EMS_TABLE`）×7ゾーン
- 各社の手数料境界（点数、注文数、Buyee の per-order 分割、ZenMarket の入金手数料の逆算）
- 免税閾値の両側（`dutyFreeLimit` / `vatFreeLimit` を跨ぐ1円差）
- `null` の伝播（未取得が 0 に化けないこと。`calc.js` の `l.amount || 0` は
  `null` を合計から落とすため、**「未取得」が総額を過小にする経路が現にある**）

### L1 — 各社の公式送料計算機との突合（実購入0件・1〜2日）

Buyee / ZenMarket は重量と国から国際送料を出す計算機を公開している。
**重量×国の格子を入れて我々の EMS 表と突き合わせれば、国際送料の表の誤差を購入0件で消せる。**
ここが合わないうちに実購入しても、何を測っているか分からない。

判定：全格子で完全一致。不一致は各社が独自マージンを乗せている証拠なので、社別の係数としてモデル化する。

### L2 — 見積時点キャプチャ（**最重要・最安**）

倉庫到着後、配達前に、各社の画面には**実測重量・三辺・parcel数・確定国内送料・国際送料見積**が出る。
配達完了を待たずにここで止めれば：

- 源#1（国内送料）の誤差＝ 予測 vs 確定国内送料
- 源#2（梱包後重量）の誤差＝ 予測重量 vs 実測重量
- 「実測重量を入れたときの国際送料」vs「予測重量を入れたときの国際送料」で、
  **重量誤差が送料誤差に幾ら化けるか**を直接測れる

**総額誤差の主要部をここで測り切れる。**配達・通関を待つ必要がない＝リードタイムが数週間短い。

### L3 — 配達完了 end-to-end（高コスト・国ごと）

実額の唯一の正解源。源#3のためだけに使う。**1カ国に集中させる**（§6）。

### L4 — 他人の請求書の収集（源#3 を唯一スケールさせられる経路）

各国の輸入時費用を自前購入で20件×7カ国揃えるのは不可能（§5）。
サイト上に「実際の請求書を投稿する」導線を作り、匿名化した明細を集める以外に道が無い。

**バイアスを明記すること**：自発投稿は高額請求・トラブル事例に偏る。
→ 投稿データは**分布の裾の把握**に使い、中心の点推定には使わない。L3 のデータで中心を固定する。

## 4. 必要サンプル数（数字で）

Clopper-Pearson 95% 片側下限：

| 観測 | 観測合格率 | 真の合格率の95%下限 |
|---|---:|---:|
| 2/3 | 66.7% | **13.5%** |
| 3/3 | 100% | 36.8% |
| 13/15 | 86.7% | 63.7% |
| 15/15 | 100% | 81.9% |
| 17/20 | 85.0% | 65.6% |
| 26/30 | 86.7% | 72.0% |
| 85/100 | 85.0% | 77.8% |

読み方：
- **「±10%以内が80%以上」を主張したければ、最低 n=15 の全件合格**。1件でも外せば主張できない。
- 現実的な合格率85%を前提に主張するなら **n≈150**。
- **国別**に主張するなら国ごとに上表が要る。7カ国×30件＝210件。§5 の費用で不可能。

→ **公開できる主張の粒度は「全体で」であって「各国で」ではない。**
現時点で「各国で実額に近い」と書けるだけの検証は、どの予算計画でも組めない。
国別は §7 の区間＋カバレッジで出す。

## 6. 国別の到達可能性

7カ国を同じ確度で扱うことはできない。`src/data.js` の `COUNTRIES` の現状で分類する：

| 国 | 未取得の項目 | 到達可能な出力 |
|---|---|---|
| SG | 通関手数料 null | 関税0・GST 9%・免税 S$400 で**ほぼ決定的**。点予測を出せる |
| AU | 関税率 null（免税 A$1,000 以下なら不要）・通関手数料 null | 低額帯は**ほぼ決定的**。点予測を出せる |
| DE / FR | 通関手数料 null（配送業者依存） | 閾値 €150 未満なら決定的。通関手数料だけ区間 |
| GB | £135 超の関税率 `dutyRate: null` | £135 未満は決定的。超えたら**出せない** |
| CA | 州税 未取得（`province_tax_not_included`）・関税率 null | **郵便番号入力が要る**。今の国だけの入力では不能 |
| US | 関税率 12.5% が `dutyVerified: false`、通関 $9.35 が `clearanceVerified: false`、de minimis 停止 | **点予測不能。区間のみ** |

→ **国ごとに「点予測を出す／区間のみ／出さない」を明示的に決める。**
全カ国を同じ画面・同じ見た目で出している現状が、最大の誤表示。
検証の順序も、決定的な国（SG / AU）から始めて計算の骨格を確定し、
不確実な国（US / CA）は最後に区間モデルとして扱う。

## 7. 点ではなく区間で評価する（合格基準の置き換え）

MAPE 中央値だけでは、**「当たらない国では何も出せない」**という結論しか出ない。
区間予測に変えれば、当たらない国でも正直に出荷できる。

各注文について記録・評価する指標：

| 指標 | 定義 | 目標 |
|---|---|---|
| 円建て絶対差 | `予測 − 実額`（円） | — |
| 絶対誤差率 | `\|予測 − 実額\| ÷ 実額` | 中央値 ≤ 8%（n≥100 でのみ主張） |
| **カバレッジ** | 実額が80%予測区間に入った率 | **75〜85%**（狭すぎも過大主張として不合格） |
| **区間幅の中央値** | 区間の広さ ÷ 実額 | 小さいほど良いがカバレッジ優先 |
| pinball loss | 分位点損失（10%/50%/90%） | モデル改善の目的関数 |
| **過小予測** | `実額 − 予測 > 0` の大きさ | 利用者が困るのは過小だけ。**非対称に重く罰する** |
| 順位一致 | 実際の最安社と予測1位の一致 | §4 の n を満たす範囲でのみ主張 |
| 出力からの脱落 | 「未取得」として総額から落とした必須費目 | **0件**（`calc.js` の `null` 脱落は現に発生しうる） |

**カバレッジで評価する利点**：米国のように点予測が不能な国でも
「¥38,000〜46,000、10件中8件はこの範囲」と出荷できる。
`REQUIREMENTS.md` §2 の「総額は約束しない」という現在の立場と、
「実額に近い総額を出す」という今回の目標を両立させる唯一の形。

**商品代が大きいほど誤差率が良く見える。**主判定は総額で行いつつ、
`総額 − 商品代`（＝モデルが実際に予測した部分）の誤差を必ず併記する。

## 8. 記録スキーマ

予測は購入・入札の**前**に固定し、後から変更できないようにする。

```jsonc
// prediction/<order_key>.json — 購入前に確定。以後変更禁止
{
  "order_key": "2026-09-14-A-neokyo-US",   // 実額レコードとの結合キー
  "frozen_at": "2026-09-14T03:11:22Z",
  "code_commit": "561f3c2",                // git commit = 改竄不能な時刻証明
  "rates_as_of": "2026-09-06",             // data.js RATES.asOf
  "input": {
    "items": [{ "url": "...", "price": 1000, "qty": 1, "seller": "...",
                "listed_domestic_shipping": 0, "free_shipping": true,
                "category": "カード", "predicted_weight_g": 50 }],
    "country": "US", "postal_code": "10001",
    "service": "neokyo", "shipping_method": "EMS",
    "consolidation": "none", "optional_services": [],
    "payment_method": "visa_credit", "billing_ccy": "USD"
  },
  "output": {
    "total_jpy": 7278,
    "interval_80_jpy": [6100, 9400],
    "lines": [ /* calc.js の lines をそのまま */ ],
    "rank": 1,
    "excluded_unknown": []                  // 「未取得」で総額から落とした費目。空であること
  },
  "hash": "sha256:..."                      // input+output の正規化ハッシュ
}
```

```jsonc
// actual/<order_key>.json — 配達完了後に確定
{
  "order_key": "2026-09-14-A-neokyo-US",
  "payments": [
    { "stage": "charge1", "date": "...", "jpy": 1350, "billed": { "ccy": "USD", "amount": 9.10 },
      "components": { "item": 1000, "service_fee": 350 }, "evidence": "evidence/xxx.pdf" },
    { "stage": "warehouse", "measured_weight_g": 180, "dims_cm": [24, 17, 3],
      "parcels": 1, "domestic_shipping_jpy": 0, "packing_jpy": 500 },
    { "stage": "charge2", "jpy": 3900, "components": { "intl_shipping": 3400, "packing": 500 } },
    { "stage": "import", "jpy": 1520, "components": { "duty": 125, "brokerage": 1395 },
      "carrier": "USPS", "terms": "DDU" }
  ],
  "refunds": [],
  "unused_balance_jpy": 0,          // ZenMarket 等の残高。費用に数えない
  "actual_total_jpy": 6770,
  "actual_total_billed": { "ccy": "USD", "amount": 45.60 },
  "complete": true                   // 証拠が1つでも欠ければ false → 別集計
}
```

**校正データと検証データの分離**：
`prediction/` を書いた後にモデルを変えた注文は、その時点で校正データに降格する。
合否判定に使えるのは「現行の計算規則で予測を固定し、その後に実額が確定した」注文だけ。
`code_commit` が現行 HEAD の祖先かどうかで機械的に判定できる。

## 10. 現行コードと本計画の前提の差分

実購入を始める前に潰す必要があるもの：

| 箇所 | 現状 | 問題 |

## 12. この計画で「言えるようになること」と「言えないこと」

| | |
|---|---|
| 言える（P3 完了時点） | 決定的な国での総額が実額の±X%以内。国内送料と梱包後重量の誤差の実測値。順位の正しさ |
| 言える（P5＋n≥100） | 全体の誤差率中央値。80%区間のカバレッジ |
| **言えない** | **「各国で」総額が実額に近いこと。**§4 の通り、国別の主張には国ごとに n≥30 が要り、§5 の費用で不可能 |
| 言えない | 請求通貨での精度。カード発行会社の上乗せはモデルの管轄外 |

**公開表示は、検証できた粒度までしか書かない。**
「実際の総額に近い」「最安会社が分かる」は、対応する n と国を併記できるまで出さない。
