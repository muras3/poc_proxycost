# proxycost — 総額算出ロジックの検証計画

対象：Buyee / ZenMarket / Neokyo / FROM JAPAN / Jauce ／ 7カ国
作成 2026-09-07。すべての指摘は本リポジトリ HEAD（`src/calc.js` / `src/data.js`）で実行して確認した。

---

## 0. 「ロジックが正しいか」は4つの別の問いである

混ぜて測ると、誤差が出たときに原因を永久に特定できない。

| | 問い | 正解の出どころ | 実購入 | 現状 |
|---|---|---|---|---|
| **Q1** | 与えられた入力から、我々の規則どおりに計算しているか（実装の正しさ） | 手計算・期待値 | 不要 | **テスト0件** |
| **Q2** | 我々の規則（料金表・EMS表・税率）が各社の公開料金と一致しているか（表の正しさ） | 各社の公式ページ・送料計算機・見積画面 | **不要** | 未実施 |
| **Q3** | 予測時点で不明な入力（国内送料・梱包後重量）の仮定が実態と合うか | 実注文の倉庫到着時の画面 | 必要（**配達は不要**） | 未実施 |
| **Q4** | 総額が実支払額と一致するか（Q1〜Q3の合成＋通関） | 配達完了後の全請求 | 必要 | 未実施 |

**Q1 と Q2 は実購入0件で終わる。**そして Q1 のテストは現在1件も無い
（`package.json` は `node --test 'test/**/*.test.js'` を実行するが `test/` が存在せず、
`npm test` は `1..0` を返して**成功扱いになる**。README の「test/calc.test.js 7件」は事実と異なる）。

Q1・Q2 を飛ばして Q4 の実購入を15件やっても、誤差 12% が出たときに
実装バグなのか料金表の転記ミスなのか重量推定なのか通関なのか、切り分けられない。
**実購入は Q3・Q4 のためだけに使う。**

## 1. オラクル（正解の出どころ）の階層

| 層 | 出どころ | 取れる粒度 | 購入 | 対象 |
|---|---|---|---|---|
| O1 | 各社の公開料金ページ | 手数料の額と課金単位 | 不要 | Q2 |
| O2 | 各社の公開送料計算機 | 重量 × 国 → 国際送料 | 不要 | Q2 |
| **O3** | **各社のカート／見積画面（決済前）** | **明細行ごとの実額** | **不要** | Q2 ＋ Q3の一部 |
| O4 | 倉庫到着後の見積画面 | 実測重量・三辺・parcel数・確定国内送料 | 必要（配達不要） | Q3 |
| O5 | 配達完了後の全請求 | 総額 | 必要 | Q4 |

**O3 が最も過小評価されている。**
5社とも、商品をカートに入れて決済ボタンを押す**前**に、手数料・国内送料・想定送料の明細が出る。
つまり **1円も払わずに、同一入力に対する各社の明細行を取得できる。**
「ロジックがある程度正しいか」に対する、最も直接的で最も安い答えはここにある。

O3 で確定できないのは2つだけ ── **実測重量（O4）** と **通関・輸入税（O5）**。
実購入が要るのはこの2つのためだけ。

## 2. 総額ではなく「明細行」で突き合わせる

`calc.js` は `lines[]` を持っている。総額だけを比較すると、
**+¥500 の誤りと −¥500 の誤りが相殺されて「合っている」ように見える。**
15件の総額比較で誤差 3% という結果が出ても、それが「2つの大きな誤りの相殺」である可能性を排除できない。

行単位で突き合わせる。我々の label と各社画面の項目名の対応表を先に作る：

| 我々の label | Buyee | ZenMarket | Neokyo | FROM JAPAN | Jauce |
|---|---|---|---|---|---|
| Items | ○ | ○ | ○ | ○ | ○ |
| Purchase fee / Service fee | ○（per order） | ○（per item） | ○（per item） | ○（per item） | ○（価格連動） |
| Domestic handling | ○ | — | — | — | — |
| Domestic shipping | ○ | ○ | **要確認** | ○ | ○ |
| Packing | 任意 | 任意 | ○（段階） | 任意 | ○ |
| Deposit fee | — | ○（%） | — | — | ○ |
| EMS | ○ | ○ | ○ | ○ | ○ |

1:1 で対応しない箇所（Buyee の per-order 分割、Neokyo の梱包料の段）は
**明示的にグループ化してから**比較する。グループの定義そのものが検証対象。

判定：
- **公開料金表に由来する行** → 完全一致（1円でも違えば不合格）
- **推定に由来する行**（国内送料・国際送料） → 誤差率を記録し、行ごとに追跡

## 3. Q1：単体テスト（実購入0件・今日できる）

### 3.1 すでに確認済みの欠陥（4件）

テストを書く前に、コードを動かして以下を再現した。**いずれも実購入なしで見つかる。**

**① EMS 表の上限超過が黙って過小評価になる**（`data.js:29-32`）

```
emsStepIndex(20000) = 26 = EMS_TABLE の最終 index
→ 20 kg の荷物が "zone 4, 1 parcel, ~15.0 kg" として ¥39,100 で計上される
```

`findIndex` が -1 のとき最終行を返すため、**表の範囲外がエラーにならず、15kg 料金に丸められる。**
表示ラベルも「~15.0 kg」と嘘をつく。範囲外は `null`＋警告にすべき。

**② 未取得（`null`）が総額から静かに落ちる**（`calc.js:122`）

```
DE 単品: Items=3000 | Service fee=350 | Domestic shipping=0 | Packing=500
       | EMS=3650 | Duty=489 | VAT=1508 | Customs clearance fee=null
total = 9497   ← 通関手数料が「—」として合計から消えている
```

`lines.reduce((a, l) => a + (l.amount || 0), 0)` が `null` を 0 として扱う。
画面は「—」と正直に出すが、**総額は必ず過小になる。**
`calc.js:115` の入金手数料の課税ベースも同じ式なので、ZenMarket の手数料も連動して過小になる。
「未取得を0と書かない」という `data.js` 冒頭の設計方針が、**総額の側で破れている。**

**③ 「注文」の数え方が商品数になっている**（`calc.js:70-76`, `120`）

```
2店舗3点 / Buyee default → parcels = 3, "¥500 × 3 orders", 通関手数料 $9.35 × 3
```

`items.length` を注文数として使っている。**item に `seller` フィールドが存在しない。**
同一店舗の2点は Buyee では1注文＝1 parcel になるはずで、
購入手数料・国内配送サービス料・parcel 数・通関手数料が**すべて過大**になる。
DE/FR の `flatDutyPerItem × n` も同じ `n` を使っている。
検証計画の「組C：2店舗から合計3商品」は、**まさにこの欠陥を踏む構成**。

**④ 内部値が文言に漏れる**（`calc.js:34`, `data.js:107`）

```
SG: {"label":"Duty","amount":0,"note":"under the SGD Infinity threshold"}
```

`dutyFreeLimit: Infinity` がそのまま利用者向けの文言に出る。

### 3.2 書くべきテスト

| 群 | 内容 |
|---|---|
| EMS | 全27段の境界（`w`, `w+1`）× 7ゾーン。**表の上限超過**。0g・負値 |
| 手数料境界 | 点数1/2/N、注文数、Buyee の per-order 分割、`stepOffset` ±1 |
| 入金手数料 | `base / (1 - r) - base` の逆算（`10000 / 0.965 = 10363` が実請求と1円差で一致：`DESIGN-NOTES.md` §3） |
| 閾値 | `dutyFreeLimit` / `vatFreeLimit` を跨ぐ1円差、両側。`Infinity` と `0` の特殊値 |
| null 伝播 | **未取得が総額に混入しない／黙って落ちない**こと。②の回帰テスト |
| 課税ベース | CIF と FOB の切り替え、VAT が duty を含むか、parcel 数の掛かり方 |
| 不変条件 | 総額 = 行の和（null を除外した旨が明示されること）／ 全行が非負 ／ 商品数を増やすと総額が単調増加 |

## 4. Q2：表の突合（実購入0件）

**4.1 O1 — 公開料金ページ vs `data.js`**
5社 × 全費目を1つの表に落として突き合わせる。GitHub Actions の週次差分検知
（`REQUIREMENTS.md` §4）は**この表が正しいことを前提にしている**ので、初回は手で全件照合する。

**4.2 O2 — 各社の送料計算機 vs `EMS_TABLE`**
重量 × 国の格子を各社の計算機に入れ、我々の EMS 表と突き合わせる。
- 完全一致 → 国際送料の誤差要因は**重量推定だけ**に絞れる（Q3 の設計が単純になる）
- 不一致 → 各社が独自マージン／独自便を持っている。社別係数としてモデル化する

**この突合をやらずに実購入すると、国際送料の誤差が「重量推定の誤差」に誤って帰属される。**

**4.3 O3 — 各社のカート／見積画面 vs `lines[]`**
同一商品URL・同一配送先で、5社すべてのカートに入れて決済直前の明細を取得する。
§2 の対応表で行ごとに比較。**これが Q2 の最終判定。**購入は発生しない。

ここで拾えるもの：
- Neokyo の ¥350 に国内送料が含まれるか（**`data.js:37` の `domesticIncluded: true` は現在まったくの未検証で、
  かつ `DESIGN-NOTES.md` §1 によれば1位が Neokyo → FROM JAPAN に入れ替わる唯一の条件がこれ**）
- ZenMarket の入金手数料が支払方法でどう変わるか（現行 `depositRate: 0.035` 固定）
- FROM JAPAN の手数料が定額か率か（現行 `perItemVerified: false`）
- Buyee が同一店舗の複数点を1注文と数えるか（欠陥③の答え）
- Jauce の価格連動手数料の実際の刻み

## 5. Q3：予測時点で不明な入力の検証（実購入は必要、配達は不要）

倉庫到着後・国際発送前の画面に、**実測重量・三辺・parcel数・確定国内送料**が出る。
ここで止めれば、配達と通関を待たずに最大の誤差源を測れる。

| 測るもの | 予測値 | 実測値 | 現行の仮定 |
|---|---|---|---|
| 国内送料 | 出品ページの表示 or 仮定 | 確定額 | `ASSUMED_DOMESTIC_SHIPPING = 800`（実勢 ¥150〜1,500 の中の一点） |
| 梱包後重量 | `商品重量 × 1.2 + 300g` | 倉庫の実測 | `PACKING_MULTIPLIER = 1.2` / `PACKING_ADD_G = 300`（`data.js` 上で仮定と明記） |
| parcel 数 | `parcelDefault` | 実際の分割 | Buyee のみ per-order（欠陥③） |

さらに **「実測重量を入れた国際送料」vs「予測重量を入れた国際送料」**を計算すれば、
**重量の誤差が送料の誤差に何円化けるか**を直接測れる。
`research/README.md` はフィギュアで重量の中央誤差 54% → 9% の改善余地を既に示しているので、
ここが最大の投資対効果。

**リードタイムが数週間短い**（配達・通関待ちが無い）ので、反復が速い。

## 6. Q4：総額の end-to-end（実購入・配達完了）

Q1〜Q3 が通ってから。測る対象は**通関・輸入税だけ**に絞られている。

正解＝同じ注文に帰属する全支払 − 返金。未使用残高は費用に数えない（入金時に失った手数料と、
その注文で消費した残高だけを配賦）。

**判定通貨は円。**カード発行会社の為替上乗せ（実勢 1.5〜3%）は利用者ごとに違い、
proxycost の管轄外。請求通貨で判定すると**測っているのは利用者の銀行であってモデルではない。**
請求通貨での差は「FX帯」として別掲する。

**商品代が大きいほど誤差率は良く見える。**主判定は総額で行いつつ、
`総額 − 商品代`（＝モデルが実際に予測した部分）の誤差を必ず併記する。

### 開始国は米国ではなく SG / AU

`data.js` の `COUNTRIES` を、通関の不確実性で分類する：

| 国 | 状態 | Q4 の適性 |
|---|---|---|
| SG | 関税0・GST 9%・免税 S$400 | **ほぼ決定的。Q3 の誤差を混入なしで測れる** |
| AU | 免税 A$1,000 以下なら関税不要・GST 10% | **ほぼ決定的** |
| DE / FR | €150 未満なら決定的。通関手数料が配送業者依存で `null` | 中 |
| GB | £135 超の `dutyRate: null` | £135 未満のみ |
| CA | 州税未取得・関税率 `null` | **郵便番号入力が必要。今の「国だけ」の入力では不能** |
| US | 関税率 12.5% が `dutyVerified: false`、通関 $9.35 が `clearanceVerified: false`、de minimis 停止 | **点予測不能。区間のみ** |

**検証計画の「全社 EMS・米国」は順序が悪い。**
米国から始めると、誤差が出たときに重量が悪いのか関税が悪いのか分離できない。
決定的な国で Q3 を確定させてから、不確実な国へ広げる。

### 点ではなく区間で評価する

米国のように点予測が構造的に不能な国がある以上、MAPE 一本では
「当たらない国では何も出せない」という結論しか出ない。

| 指標 | 定義 | 目標 |
|---|---|---|
| 絶対誤差率 | `\|予測 − 実額\| ÷ 実額`（円） | 中央値 ≤ 8%（n が足りるときのみ主張） |
| **カバレッジ** | 実額が80%予測区間に入った率 | **75〜85%**（狭すぎるのも過大主張として不合格） |
| 区間幅 | 区間の広さ ÷ 実額 | 小さいほど良いがカバレッジ優先 |
| pinball loss | 分位点損失（10/50/90%） | モデル改善の目的関数 |
| **過小予測** | `実額 − 予測 > 0` の大きさ | 利用者が困るのは過小だけ。**非対称に重く罰する** |
| 出力からの脱落 | 「未取得」として総額から落とした必須費目 | **0件**（欠陥②の回帰） |

カバレッジで評価すれば、米国でも「¥38,000〜46,000、10件中8件はこの範囲」と正直に出せる。

## 7. 何件で「ある程度正しい」と言えるか

Clopper-Pearson 95% 片側下限：

| 観測 | 観測合格率 | 真の合格率の95%下限 |
|---|---:|---:|
| 2/3 | 66.7% | **13.5%** |
| 3/3 | 100% | 36.8% |
| 13/15 | 86.7% | 63.7% |
| 15/15 | 100% | 81.9% |
| 26/30 | 86.7% | 72.0% |
| 85/100 | 85.0% | 77.8% |

- 検証計画の**「各社3件のうち2件以上が±10%」は、真の合格率 13.5% でも通る。**事実上の無検定。
- 「15件で15%超の過小予測が0件」でも、真の失敗率は**最大 18.1%** まで許容される（rule of three）。
- n=15 の中央値の95%CIは**4番目〜12番目の順位統計量**、つまり分布のほぼ全域。
  「誤差率中央値8%以下」を n=15 で判定する分解能は無い。
- 「±10%以内が80%以上」を主張するには**全件合格でも n≥15**、現実的な合格率85%なら **n≈150**。
- **国別**に主張するなら国ごとに上表が要る。7カ国 × 30件 = 210件。

→ **n=15 の正しい位置づけは合否判定ではなく「符号の大きい欠陥の探索」。合格基準を書いてはいけない。**
そして Q1・Q2 で見つかる欠陥（§3.1 で既に4件）は、n=15 の探索より安く確実に見つかる。

実購入のサンプル数を制約するのは費用：米国宛15件で **¥176,299**（現行4社・proxycost 自身の見積）。
7カ国 × 30件は約 ¥300万。**「各国で」の主張は、どの現実的な購入計画でも支えられない。**
国別は §6 の区間＋カバレッジで出す。

## 8. 予測の固定と、校正／検証の分離

購入・入札の**前**に予測を固定し、後から変更できないようにする。

```jsonc
// prediction/<order_key>.json — 購入前に確定。以後変更禁止
{
  "order_key": "2026-09-14-A-neokyo-SG",
  "frozen_at": "2026-09-14T03:11:22Z",
  "code_commit": "561f3c2",              // git commit = 改竄不能な時刻証明
  "rates_as_of": "2026-09-06",           // data.js RATES.asOf
  "input": {
    "items": [{ "url": "...", "price": 1000, "qty": 1, "seller": "...",
                "listed_domestic_shipping": 0, "free_shipping": true,
                "category": "カード", "predicted_weight_g": 50 }],
    "country": "SG", "postal_code": "...",
    "service": "neokyo", "shipping_method": "EMS",
    "consolidation": "none", "optional_services": [],
    "payment_method": "visa_credit", "billing_ccy": "SGD"
  },
  "output": {
    "total_jpy": 7278, "interval_80_jpy": [6100, 9400],
    "lines": [ /* calc.js の lines をそのまま */ ],
    "rank": 1,
    "excluded_unknown": []               // null で総額から落ちた費目。空であること（欠陥②）
  },
  "hash": "sha256:..."
}
```

```jsonc
// actual/<order_key>.json — 段階ごとに追記
{
  "order_key": "2026-09-14-A-neokyo-SG",
  "stages": {
    "cart":      { "lines": [ /* O3: 決済前の画面 */ ] },
    "charge1":   { "jpy": 1350, "billed": { "ccy": "SGD", "amount": 11.6 }, "evidence": "..." },
    "warehouse": { "measured_weight_g": 180, "dims_cm": [24,17,3], "parcels": 1,
                   "domestic_shipping_jpy": 0, "packing_jpy": 500 },   // O4: Q3 の正解
    "charge2":   { "jpy": 3900, "components": { "intl_shipping": 3400, "packing": 500 } },
    "import":    { "jpy": 0, "carrier": "SingPost", "terms": "DDU" }   // O5: Q4 の正解
  },
  "refunds": [], "unused_balance_jpy": 0,
  "actual_total_jpy": 5750,
  "complete": true    // 証拠が1つでも欠ければ false → 「正解データ不完全」として別集計
}
```

**校正と検証の分離**：`prediction/` を書いた後にモデルを変えた注文は、その時点で**校正データに降格**する。
合否に使えるのは「現行の計算規則で予測を固定し、その後に実額が確定した」注文だけ。
`code_commit` が現行 HEAD の祖先かどうかで機械的に判定できる。
