## 0. 要旨（決めたこと）

1. **教師データの定義を変える。** 学ぶべき写像は「タイトル → グラム」ではなく **「タイトル → ライン」** と **「ライン → 重量分布」** の
   2 つで、前者の教師は本番の実タイトルに人が付ける `expectLine`（`data/weights-corpus.json`、既に始まっている）、後者の教師は
   Shopify の usable なスライス（既存の `shopify-probe --slice`）。**この 2 つは別の言語・別の母集団から来るので、1 本の学習器で繋げない。**
2. **実行時の引き当ては辞書のまま。** 学習ベース（k-NN）は実行時に**採らない**。理由は精度でも索引サイズでもなく、
   **教師データの言語が違う**こと（§2）。grams を公開している店のタイトルは英語かローマ字で、本番が渡す題名は日本語。
   実測: 日本語タイトル 37 件を英語カタログ 5,000 件の索引に当てると、英数字トークン（'1/4' 等）を共有する数件を除いて近傍はでたらめだった（§3.2）。
3. **k-NN は build 時の道具として採る。** 取りこぼした題名に近いカタログ行を人に見せ、ライン・語・スライスを提案する
   `scripts/weights-neighbors.ts`（§1.5）。決定的で、間違いは人が止められる。
4. **棄権は 3 か所で、閾値はすべて既存の数から借りる。** (a) 語が当たらない／門で落ちる → `null`（現状どおり）。
   (b) 店頭・カテゴリページを名指す題名 → `null`（新設。母数 17 件のうち 4 件に今は重量が付く）。
   (c) **新しいラインは P75/P25 ≤ 3 かつ n ≥ 50 でなければ足せない**（既存の `rankStable` の ×1/3〜×3 と probe の n<50 をそのまま使う。
   LOO 実測で P75/P25 が 3 を超えると ×3 超の外れが 4.5% → 12% に跳ねる。§5）。
5. **索引サイズは制約ではなくなった。** Cloudflare は 2026-09-04 に圧縮後上限（3/10 MB）を撤廃し、非圧縮 64 MiB のみ（§4）。
   ただし引き当ては `'use client'` の中で走るので、索引は**利用者のダウンロード**に乗る。実測で 5,000 行 = 0.9 MB gzip、
   16,719 行 = 1.6 MB gzip。今の `src/data/weights.ts` は 110 KB。載るが、要らない。
6. **根拠の見せ方は変えない。** 辞書のヒットは `estimate`（`~`・琥珀）で `1/7 scale · n=647 · 1.0x · solarisjapan.com`。
   もし将来 k-NN を出すなら、それも `estimate` であって `unverified` ではない（§6）。ただし近傍の題名を見せることは
   「生カタログを再配布しない」判断と衝突する——k-NN が満たせないのは決定性ではなく**根拠の開示**のほう。
7. **移行は 5 段。** 固定 → 母数の運用 → 店頭門 → build の門 → 近傍ツール。実行時 k-NN は第 6 段として**条件付き**で置く（§8）。

## 1. 決めた設計

### 1.1 データの流れ

```
本番 /api/search の実タイトル ──人が kind と expectLine を付ける──▶ data/weights-corpus.json     … 教師 A: タイトル→ライン
                                                                        │
Shopify products.json ──shopify-probe --dump──▶ (ローカルのみ、git に入れない)                   │
        │                                                               │
        ├─ --slice で判定 usable/suspect ──▶ data/weights/<category>.json（ライン＝中央値・四分位・n・語）… 教師 B: ライン→重量
        │                                       │
        └─ weights-neighbors.ts（k-NN、build 時） ┼──▶ 人に「この取りこぼしに近い行」を見せる。人が語とスライスを決める
                                                │
                                   weights-build.ts ──▶ src/data/weights.ts（生成物）
                                                │
                                   resolveWeight()（ブラウザ、辞書＋門） ──▶ grams / null
                                                │
                              weights-coverage.ts + weights.corpus.test.ts が corpus で毎回測る
```

今と違うのは 3 点だけ: corpus を**主要な教師データとして運用する**こと、build に**足せるラインの門**を置くこと、
k-NN を**人の道具**として置くこと。実行時の経路は変わらない。

### 1.2 母数（`data/weights-corpus.json`）の意味づけ

別エージェントが 2026-09-07 に `kind` と `expectLine` を入れた。ここに 1 種類足す。

| kind | 意味 | 引き当ての期待 | 率の分母に |
|---|---|---|---|
| `listing` | 1 点の商品で、**その物の重量データが表にある** | `expectLine` の行 | 入る |
| `listing-no-data`（新設） | 1 点の商品だが、そのカテゴリ・穴が `notObtained` / `partialGaps` にある | `null` | **入れない**。ただし別に数える |
| `off-target` | 店頭・カテゴリページ・別ジャンル | `null` | 入れない。**0 件であること**を検査する |

今の 37 件をこの 3 つに分けると: `off-target` 17、`listing` 16、`listing-no-data` 4（Web カメラ＝cameras 未取得、
メンズコーデセット＝apparel 未取得、携帯ゲーム機 2 件＝games の穴、n=26 で 400〜4,100 g）。
**作業ツリーの resolver は `listing` 16/16 を当て、`off-target` 17 件のうち 4 件に重量を付けている。**
依頼文の「9/37 = 24%」は `60b7c59` より前の測定で、分母に店頭ページを含めていた。

つまり残りの取りこぼしは**全部データの天井**で、引き当てアルゴリズムの問題ではない。この事実が §2 の判断の土台。

率は 3 つ出す（`weights-coverage.ts` の拡張）:
- `resolved / listing`（引き当て率。今 16/16）
- `off-target resolved`（誤爆。今 4/17。**目標 0**）
- `listing-no-data / (listing + listing-no-data)`（データの穴。今 4/20。これは取得の仕事）

### 1.3 引き当ての手順（実行時）

現状の `resolveWeight` の 2 段（個別ライン → 総称ライン）と門（corroboration / exclusion）を踏襲する。足すのは 1 段だけ:

```
0. 店頭・カテゴリページの門（新設、§1.4）     → 該当すれば null
1. 個別ライン: 語の最長一致 + corroboration + exclusion
2. 総称ライン: 1 で何も当たらなければ
3. 何も当たらなければ null → 呼び出し側が ASSUMED_WEIGHT_G（1,000 g・'assumed'）
```

Aho–Corasick に置き換えない。75 ライン・508 語で **0.44 ms／題名**（37 件 × 200 回の実測）。速度の問題は無い。

### 1.4 店頭・カテゴリページの門

母数の `off-target` 17 件のうち重量が付いた 4 件:

| 題名 | 今の結果 | なぜ店頭と分かるか |
|---|---|---|
| `スニーカー - ハニーズ Yahoo!店` | 750 g | 末尾 `Yahoo!店` |
| `【楽天市場】シューズ・靴 > スニーカー：SHOPLIST` | 750 g | パンくず `>` と末尾 `：店名` |
| `駿河屋Yahoo!店 - フィギュア` | 800 g | `Yahoo!店` |
| `五番街〜バッグ・財布のお店` | 235 g | `のお店` |

門の形は `EXCLUSIONS` の `allCategories` と同じ（「タイトルが別の物を名指ししている」の一種）。`when` に
`Yahoo!店`、`楽天市場店`、`のお店`、`｜Yahoo!ショッピング` 末尾、`【楽天市場】…>…：` のパンくず形を置く。
**語ではなく形（末尾・区切り）で見る**——`スニーカー` や `フィギュア` は商品にも店頭にも出るので語では分けられない。
完了条件は `off-target resolved = 0/17` と、`listing` 16 件が 1 件も落ちないこと。

これは「検索側の問題」でもある（別エージェントの注記どおり）。だが resolver がタダで拒めるものを通す理由は無い。
検索側が店頭を返さなくなったら門は死ぬだけで害は無い。

### 1.5 build 時の近傍ツール `scripts/weights-neighbors.ts`

```
npx tsx scripts/weights-neighbors.ts --from dumps/*.json "腕時計 アナログウォッチ ブラック"
```

- 入力: `shopify-probe --dump` で置いたローカルの生行（複数店可）と、取りこぼした題名 1 件以上。
- 処理: NFKC → 小文字 → 市場の定型句除去 → 空白区切りトークン内の文字 2/3-gram → TF-IDF（対数 idf、L2 正規化）→ cosine 上位 k=20。
- 出力: 近傍 20 行の題名・grams・店、中央値・P25–P75・P75/P25、top-1 cosine。**数字を表に書くことはしない。**
  人がそれを見て `--slice` の語を決め、probe の判定（usable/suspect/pseudo、n ≥ 50）を通してからラインにする。
- 決定的（同じダンプ・同じ題名なら同じ出力）。ネットワークを使わない。LLM も使わない。

役割は「語を思いつく」工程の補助であって、判断はしない。§3.2 の実測どおり、言語が違えば近傍はでたらめになるが、
それは**人が一目で分かる**種類の間違いで、画面に出る間違いではない。

### 1.6 build の門（`weights-build.ts` に足す検査）

| 検査 | 今の違反 | 根拠 |
|---|---|---|
| ラインの `n ≥ 50`（`n = 0` の「記録していない」は別扱いで残す） | used-luxury の鞄 6 ライン（n = 8〜34） | probe が `insufficient` とする閾値と同じ |
| **新規**ラインは `spread ≤ 3` | 既存 5 ライン（jig-head 7.0x、fishing-line 5.6x、kendo-do 5.0x、soft-bait 4.3x、snack-sweets 3.1x）。**既存は消さない**（§5.3） | `rankStable` の ×3 と LOO の膝（§5） |
| `sourceDomain` の verdict が `pseudo` でない | 無し | index.json の方針どおり |
| JSON → TS のドリフト検査（vitest で再生成して比較） | 検査自体が無い（DESIGN-FEES-DATA §2 が指摘） | 料金側と同じ |
| 新しい `match` 語は corpus の `off-target` を 1 件も当てない | 4 件（§1.4 で解消） | 誤爆は取りこぼしより危険（logic.md §5） |

## 2. 教師データの判断: 弱いラベルで学習に行くか、辞書を伸ばすか

**結論: 辞書を伸ばす。学習ベースは実行時に採らない。** 理由は 3 つで、強い順に書く。

### 2.1 教師データの言語が違う（決定的）

grams を公開している Shopify 店のタイトルを数えた（2026-09-07、`products.json` 1 ページ 250 件、または全件ダンプ）:

| 店 | verdict | 日本語文字を含むタイトル |
|---|---|---:|
| jpbookstore.com | usable | **0 / 5,000** |
| japan-figure.com | usable | **0 / 9,078** |
| www.solarisjapan.com | usable | **1 / 5,000** |
| kplaceshop.com | usable | 31 / 2,467 |
| kokorojapanstore.com / wabisabi-store.jp | usable | 0 / 250 ずつ |
| luxlux.jp / tozandoshop.com | suspect | 2 / 250、3 / 250 |
| kpopmerch.jp | **suspect** | 141 / 250 |
| www.kendo.co.jp | **suspect** | 250 / 250 |

usable な店は海外向けで**題名が英語かローマ字**。日本語の題名を持つ店は 2 つしか無く、**両方 suspect**。
本番が resolver に渡す題名は 37 件中 37 件が日本語文字を含む（ヤフオク・メルカリ・楽天・Amazon.co.jp）。

文字 n-gram の TF-IDF は単語境界が要らないが、**文字が共有されていなければ何も測れない**。「腕時計 アナログウォッチ」と
"Luxury Watch Seiko" に共通の 3-gram は無い。だから学習器の精度をいくら上げても、本番の入力に対しては動かない。
これは §3.2 で実際に確かめた。

### 2.2 ラベルは「その店の梱包区分」で、本番の物とは別物

Shopify の grams は実測ではない（`src/data/weights.ts` 冒頭）。それでもラインの中央値として使えるのは、
**同じ店の同じ区分で揃えているから**。k-NN は店を跨いで近傍を取るので、この前提が崩れる。

- 4 店を合わせた索引（16,719 行）の LOO で、**top-1 cosine ≥ 0.9 の近傍（ほぼ同じ題名）でも 10.9% が ×3 超で外れる**。
  同じ商品が店ごとに別の送料帯に置かれている。単一店（Solaris）では同じ区間で 2.1%。
- kendo.co.jp の grams は 100 倍ずれている（「竹刀 完成品」の近傍中央値 **200,000 g**）。suspect の店をそのまま
  教師にすると、こういう値が 20 近傍の中央値として出る。probe の判定を通した**スライス**でしか使えない、という今の方針は正しい。
- 新品と中古、箱ありと無しは、どの学習器でも題名からは分からない。k-NN なら「箱無し」の語で近傍が変わる可能性はあるが、
  教師側（Shopify 新品）に箱無しの行が無いので学べない。

### 2.3 辞書の限界費用が今はまだ低い

- この 1 日で辞書は出品 20 件のうち **5 件 → 16 件**へ動いた（`60b7c59` のコミット本文に着手前の実測 5/20 がある。
  その後 `140f53b` → `3b59120` ＋ 作業ツリー）。ラインは 69 → 75 本。
- 残りの取りこぼしはデータの天井（§1.2）。学習器も辞書も同じ天井に当たる。
- 辞書の弱点「語を足すと誤爆が増える」（logic.md §5 の 13 件）は、corpus の `off-target` と誤爆 13 件を**テストとして
  固定すれば**回帰として捕まる。今は捕まっている（`weights.corpus.test.ts`、`weights.test.ts`）。

### 2.4 では教師データはどう強くするか

「タイトル → グラム」の日本語データは存在しないので作らない。作れるのは 2 つ:

1. **タイトル → ライン**（corpus）。本番の題名に人が `expectLine` を付ける。1 件 10 秒。言語は本番と同じ。
   ラベルの正しさは人が保証する。**これが学習ベースを含むどんな方式でも最終的に必要な、唯一の本番分布の教師。**
2. **ライン → 重量分布**（probe のスライス）。これは今のまま。強くする手段は店を増やすことではなく
   （162 ドメイン叩いて usable 34）、**スライスの切り方**を細かくすること（figures を scale で切ったら spread 1.0x になった実績）。

利用者が入力した重量（`weightOrigin: 'user'`）を教師にする案は、本番分布の日本語ラベルになる唯一の道だが、
同意・保存・品質のどれも今は無い。§8 の第 6 段の前提条件に置くだけで、設計には入れない。

## 3. 依頼の仮説（辞書 → k-NN → 棄権）を採るか

**辞書と棄権は採る。実行時 k-NN は採らない。k-NN は build 時に採る。**

### 3.1 仮説の正しいところ

- 「辞書で頭、別の手で裾」という分担は正しい。裾を取る手が k-NN であること自体も、根拠が四分位で出る点で正しい。
- **近傍の P75/P25 は誤差をよく予言する。** これは実測で確かめた（§5.1）。棄権の信号として使える。
- 線形モデルの係数を見せられない、という判断も正しい。

### 3.2 仮説が外れるところ（実測）

本番の実タイトル 37 件を、Solaris 5,000 行の索引に当てた:

- top-1 cosine は **0.13〜0.48**。同じ索引での LOO（同じ店の題名どうし）では 97% が 0.4 以上、93% が 0.5 以上。
  つまり本番の題名は索引の分布の外にいる。
- 近傍の中身: 「カメラを止めるな! [Blu-ray]」→ 鬼滅の Blu-ray と 3 g のカード、中央値 3 g。「腕時計の図鑑」→ ワンピースカード、
  中央値 880 g（P75/P25 1.6 — **分散の門を通る**）。「realromantic SORA トレカ」→ 1/7 スケールフィギュア 1,500 g。
  まともに見えたのは「YEMEIZHEN 変態フィギュア … 1/4」→ 1/4 の近傍で 2,225 g（1,500〜3,000）のような、'1/4' という**英数字を
  共有した**数件だけで、それは辞書の `scale-1-4` が既に 3,000 g で当てている。
- 日本語の索引（kendo.co.jp + kpopmerch.jp、1,600 行）に当てると: 「SEVENTEEN ペンライト 公式 ver.3」は top-1 **0.75** で
  800〜1,000 g（正しい形）。「BOYNEXTDOOR … トレカ」は 0.48 でアルバム 800 g（トレカ 1 枚ではない——**店に無い物は近傍に無い**）。
  「剣道 袴」は 0.37 で **200,000 g**（店の grams が擬似値）。

言語が揃えば形は動く。揃っていなければ、**分散の門も類似度の門も通り抜ける自信たっぷりの誤りが出る**（880 g の図鑑）。
「近傍が不整合なら棄権」は、近傍が**整合して間違っている**ときに効かない。

### 3.3 k-NN の置き場所

したがって k-NN は**人の目の前**に置く（§1.5）。そこなら「腕時計の図鑑にワンピースカードが出た」は笑って捨てられる。
実行時に出せば、その 880 g は `~880 g` として画面に載る。

### 3.4 「TF-IDF と最近傍は決定的なので規約に触れない」の線引きは妥当か

規約の目的を 3 つに分けると答えが出る:

| 目的 | TF-IDF + k-NN は | 補足 |
|---|---|---|
| 再実行で同じ結果 | **満たす**。索引を build 時に固定すれば決定的 | ただし `String.prototype.normalize('NFKC')` と `toLowerCase()` は実行環境の Unicode 版に依存する。索引のチェックサムを CI で固定し、ブラウザ側では**索引に入っている n-gram しか使わない**ので実害は出にくいが、ゼロではない |
| ネットワーク・外部モデルに依存しない | **満たす** | |
| **根拠を利用者に見せられる** | **満たさない（この製品では）** | 「似ている 20 件は 380〜600 g」の 20 件を見せるには**生カタログの題名を配布する**ことになる。「生カタログは再配布しない」（`src/data/weights.ts` 冒頭）と衝突。数字だけ（n・中央値・四分位）にすれば辞書のラインと同じ形になり、それなら辞書でよい |

線引きは妥当。ただし「決定的だから可」で止めると 3 つ目を見落とす。**k-NN が満たせないのは決定性ではなく開示。**

## 4. 索引サイズの見積もり（実測）

### 4.1 前提が変わった

- Cloudflare Workers: **2026-09-04 の変更で圧縮後の上限（Free 3 MB / Paid 10 MB）は撤廃。非圧縮 64 MiB のみ**、全プラン共通。
  残る制約は **起動 1 秒**（グローバルスコープの実行）、**メモリ 128 MB**、**CPU 時間 Free 10 ms／リクエスト**（Paid 5 分）。
- `resolveWeight` は `ItemList.tsx` / `useCompare.ts`（どちらも `'use client'`）から呼ばれる。**引き当てはブラウザで走る。**
  索引は Worker のバンドル（SSR）にも、利用者のダウンロードにも乗る。

### 4.2 測った値

文字 2/3-gram、df ≥ 2、L2 正規化、CSR（varint の差分 id ＋ u8 重み）。数字は実際に組んだバイト列と gzip の長さ。

| 索引 | 行数 N | 語彙 V | nnz | ベクトル raw | gzip | brotli | 題名 raw / gzip | 1 行あたり raw / gzip |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Solaris のみ | 4,988 | 7,095 | 616,156 | 1,291 KB | 906 KB | 742 KB | 399 / 98 KB | 356 / 212 B |
| 4 店合算（df ≤ 10% で刈る） | 16,719 | 10,426 | 929,296 | 2,178 KB | 1,599 KB | 1,414 KB | 1,057 / 294 KB | 203 / 119 B |
| 日本語 2 店 | 1,600 | 6,842 | 108,584 | 232 KB | 157 KB | 144 KB | 91 / 26 KB | 237 / 133 B |

- **2.2〜2.4 バイト／非零要素**。1 行あたり 54〜120 個の非零要素（刈り方次第）。
- 外挿（ベクトルだけで 1 行 133〜265 B raw / 98〜186 B gzip、線形）: **3 万行 ≈ 4〜8 MB raw ≈ 2.9〜5.6 MB gzip、
  5 万行 ≈ 6.7〜13 MB raw ≈ 4.9〜9.3 MB gzip**。64 MiB には載る。
- 比較: 今の `src/data/weights.ts` は **110 KB**。k-NN 索引はその 10〜60 倍。

### 4.3 別の持ち方

- **題名と grams だけ配って起動時に索引を組む**: 16,719 行で 1,089 KB raw / 310 KB gzip。だが特徴量化に **256 ms**（node、単一スレッド）。
  5 万行なら約 770 ms で Worker の起動 1 秒に触れ、ブラウザではメインスレッドを塞ぐ。
- **問い合わせ時間**: 転置索引の素朴な走査で 5,000 行 18.6 ms、16,719 行（刈り済み）14.5 ms、1,600 行 0.41 ms。
  Free プランの CPU 10 ms を超えるので**サーバで引くなら Paid が前提**。ブラウザなら 1 品の追加ごとに 15 ms は許容。
- **ライン単位の重心（75 本）**: 数十 KB。だがこれは「辞書の語を n-gram に溶かしたもの」で、誤爆の制御が語より難しくなる。却下（§7）。

### 4.4 結論

載る。ただし §2 の理由で要らない。載るか載らないかが論点だった前提は、Cloudflare の変更と「ブラウザで走る」の 2 点で崩れている。
**索引の重さより、辞書 110 KB を 20 倍にしてまで得るものが無い**のが実態。

## 5. 棄権の閾値の決め方

### 5.1 実測: 近傍の P75/P25 と外れ率（Solaris 4,988 行、LOO、k=20）

| 近傍の P75/P25 | 割合 | 中央値が ×1.25 以内 | ×2 以内 | **×3 超の外れ** |
|---|---:|---:|---:|---:|
| = 1.0 | 18.5% | 89% | 97% | 1.2% |
| 1.0–1.25 | 22.3% | 79% | 95% | 0.9% |
| 1.25–1.5 | 14.9% | 66% | 93% | 1.5% |
| 1.5–2 | 26.1% | 58% | 91% | 2.4% |
| 2–3 | 14.7% | 40% | 83% | **4.5%** |
| 3–5 | 3.3% | 38% | 72% | **12.2%** |
| > 5 | 0.3% | 33% | 60% | 13.3% |

4 店合算では同じ形で数字が悪くなる（2–3: 8.6%、3–5: 17.7%、>5: **39.4%**）。
一方 **top-1 cosine は同一店内では誤差と無関係**（0.3〜1.0 のどの区間でも ×1.25 以内が 62〜69%）。
類似度は「分布の中にいるか」を、分散は「答えが定まっているか」を測る。別の量。

### 5.2 閾値の出し方（恣意性を避ける）

数字を新しく決めない。**製品に既にある 2 つの数と、probe に既にある 1 つの数を借りる。**

| 閾値 | 値 | どこから借りるか | 実測との整合 |
|---|---|---|---|
| ラインの幅 | **P75/P25 ≤ 3** | `compare.ts` の `rankStable` が「重量を ×1/3〜×3 に振っても 1 位が動かないか」で判定する。**中央値の四分位が製品自身の許容幅を超えるラインは、製品の判定を壊す** | 5.1 の膝と一致（2–3 で 4.5%、3–5 で 12%）。偶然の一致ではなく、どちらも「×3 を超えて外れると順位が変わる」という同じ事実の表れ |
| サンプル数 | **n ≥ 50** | `shopify-probe.mjs judge()` の `insufficient` | 既存 |
| 類似度（k-NN を出すなら） | **同分布 LOO の top-1 の 5 パーセンタイル** | 「分布の中の問い合わせを 5% 以上棄権しない」という定義。Solaris で ≈ 0.45 | 本番 37 件の最大 0.48 は**この門をほぼ通らないが、通る例がある**（0.48 の BOYNEXTDOOR）。**類似度の門は分布の外を完全には止めない**（§3.2） |

### 5.3 既存の 5 ラインをどうするか

spread > 3 のラインは jig-head（7.0x）、fishing-line（5.6x）、kendo-do（5.0x）、soft-bait（4.3x）、snack-sweets（3.1x）。
**消さない。** 理由は docs/UI-DESIGN.md §4 が「幅の広いラインは `weightSensitivity` が名指しする」で既に受けているから。
門は**新規ラインの追加**にだけ掛ける。既存の 5 本は `index.json` に `wideLines` として列挙し、`/weights` に出す。
分割できるなら分割する（figures を scale で切って 1.0x になったのと同じ手。kendo-do は「入門用／高級」のような語で切れるかを
`--slice` で試す価値がある）。

### 5.4 実行時の棄権

変えない。語が無い・門で落ちる → `null` → 呼び出し側が 1,000 g を `'assumed'` で入れる。
§1.4 の店頭門が加わるだけ。「分からない」と言う場所は resolver（`null`）で、それをどう見せるかは UI（§9 の 1 行目）。

## 6. 根拠の見せ方と確度 4 段階

| 出所 | tier | 表示（UI-DESIGN §6 の規定どおり） | 根拠の行 |
|---|---|---|---|
| 辞書のライン | `estimate` | `~1,500 g`（琥珀） | `1/7 scale · n=647 · 1.0x · solarisjapan.com`、`middle half 1.5 kg`。今のまま |
| 仮置き | `estimate` | `~1,000 g` | `assumed — no weight data for this title`。今のまま（UI-DESIGN §4） |
| 利用者入力 | `estimate` + `✎` | `~439 g ✎` | 出所を外す。今のまま |
| **近傍の中央値（もし出すなら）** | **`estimate`** | `~439 g` | `20 similar catalogue listings · middle half 380–600 g · 2 stores`。**題名は出さない**（再配布しない） |

近傍の中央値を `unverified` にしない理由: `unverified` は「二次情報」（他人の数字を引いた）であって「我々の推定の弱いもの」ではない。
近傍の統計は我々が一次のカタログから自分で出した数字で、ラインの中央値と同じ立場。**確度の軸に「推定の強弱」は無い**（DESIGN-NOTES §2 の 2 軸は「発生の確実さ」と「金額の確実さ」）。
推定の強弱は tier ではなく **`weightSensitivity`**（その品の幅で 1 位が動くか）で伝える設計になっていて、これは近傍にもそのまま使える
（P25–P75 を渡すだけ）。

「なぜ 439 g か」への答えは今も将来も同じ形: **どの母集団の、何件の、どの四分位か。** 辞書ならライン名がそれを言い、
近傍なら店名と件数がそれを言う。題名を出さなくても答えられる。

## 7. 却下した案とその理由

| # | 案 | 却下の理由 |
|---|---|---|
| 1 | **実行時 k-NN（依頼の仮説の 2 段目）** | 教師の言語が違う（§2.1）。本番 37 件で top-1 0.13〜0.48、近傍は英数字を共有する数件を除いてでたらめ、うち「腕時計の図鑑 → 880 g」は分散の門を通る（§3.2）。店を跨ぐと近い題名でも 11% が ×3 超（§2.2）。載るが要らない（§4） |
| 2 | **n-gram の線形回帰／勾配ブースティング** | 係数を利用者に見せられない（依頼文の指摘どおり）。教師データの問題は k-NN と同じ。決定性は満たすが根拠を満たさない |
| 3 | **外部埋め込み API・LLM** | 規約。加えてモデル版が変わると同じ題名で違う値が出る。再実行の同一性が保てない |
| 4 | **カテゴリ分類器 → `fallbackG`** | `fallbackG` は今アプリから到達しない死んだ経路（logic.md §5）。カテゴリ平均には幅が無く `weightSensitivity` に渡せない。「表全体の中央値を仮置きにする」が UI-DESIGN §4 で却下された理由（ルアーとカードに引かれる）と同じ欠陥をカテゴリ単位で持つ |
| 5 | **Aho–Corasick で辞書を高速化** | 508 語で 0.44 ms／題名。速度は問題ではない。正規表現の境界処理（`PSA10` の英数境界）を Aho–Corasick に持ち込むと複雑になるだけ |
| 6 | **形態素解析（kuromoji 等）で単語境界を切る** | 辞書は部分一致で日本語を当てており、境界は要らない。辞書ファイルが数 MB〜十数 MB で、§4 の索引より重い |
| 7 | **suspect の店の行を教師に入れて母数を増やす** | kendo.co.jp の grams は 100 倍ずれている（近傍中央値 200,000 g）。probe の判定を通さない行は、n が増えるほど害が増える |
| 8 | **Shopify の `product_type` をラベルにした分類器** | 型は店ごとの都合。Solaris の `Figure` は 9,893 件で 1/4（3,000 g）からねんどろいど（439 g）まで含む。分類できても重量は決まらない |
| 9 | **ライン重心 75 本の近傍（小さな k-NN）** | 辞書の語を n-gram に溶かしたもの。「1/7」が「11/4」に当たる類の誤爆を、語の境界規則ではなく類似度の閾値で止めることになり、logic.md §5 の 13 件を制御できない |
| 10 | **生カタログを配って近傍の題名を根拠として見せる** | 「生カタログは再配布しない」判断と衝突。相手は他社の商品データ。数字だけ出すなら辞書と同じ形になる（§3.4） |
| 11 | **`match` 語を JSON から外して corroboration / exclusion も JSON に移す** | DESIGN-FEES-DATA §2 が決めた原則「データは判断を持たない、判断はコード」に反する。門の `why` は英文で書かれていて、テストが名指ししやすい今の置き場が正しい |

## 付録 A — 測り方（再現できるように）

環境: node v22.22.2、2026-09-07。データはすべてこの日に取得または既にリポジトリにあったもの。

**データ**
- `research/weights-solarisjapan.json`（5,000 行、英語）。
- `node scripts/shopify-probe.mjs <domain> --pages N --dump <file>` で jpbookstore.com（5,000 行）、japan-figure.com（9,078）、
  kplaceshop.com（2,467）、www.kendo.co.jp（2,528）、kpopmerch.jp（2,885）を取得。ダンプはローカルのみ、コミットしていない。
- 本番題名 37 件: `data/weights-corpus.json` の `title` そのまま。

**特徴量**: NFKC → 小文字 → 先頭の `Amazon.co.jp:` / `【楽天市場】` と末尾の ` - メルカリ` 等の定型句を除く → 空白でトークン →
各トークンを `_` で囲み文字 2-gram と 3-gram → df ≥ 2（4 店合算では df ≤ 10% も）→ `(1 + log tf) × (log((N+1)/(df+1)) + 1)` → L2 正規化。

**近傍**: 転置索引で cosine、k = 20、自分自身を除く（LOO）。予測は近傍 grams の中央値、幅は P25–P75。
「(正規化した題名, grams) が同じ行」は 1 行に潰した（variants の重複）。

**評価**: 予測／実測の比が [1/1.25, 1.25]・[1/2, 2] に入る割合、[1/3, 3] の外に出る割合、実測が近傍の P25–P75 に入る割合。
Solaris は全 4,988 件、4 店合算は 5 件おきの 3,344 件、日本語 2 店は全 1,599 件。

**索引サイズ**: 行ごとに varint(非零数)、varint(語 id の差分)、u8(重み × 255) を並べたバイト列の長さと、その `zlib.gzipSync(level 9)` /
