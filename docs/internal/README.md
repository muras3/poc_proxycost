## caveat-register.csv / caveat-register.xlsx

`docs/design/caveat-coverage-audit.md`（注意事項100件の網羅性監査）・`docs/design/caveat-ui-grammar.md`（視覚の文法・7手段の設計判断）・`docs/design/mock-v3-caveat-map.md`（`prototypes/mock-v3.html` での実装状況）を突き合わせて作った、100件全件の状態一覧。

- 2ファイルは同じ内容。`.csv` は UTF-8 BOM 付きで Excel / Google スプレッドシートでそのまま開ける。`.xlsx` は先頭行固定・オートフィルタ・列幅調整・UI区分ごとの色分け済み。
- 元の3文書のどれも更新されたら、この台帳は古くなる。台帳を直接編集せず、まず元の3文書を直してから台帳に反映すること（台帳はコードや設計判断そのものではなく、突き合わせの記録）。

### 列の定義

| 列 | 意味 |
|---|---|
| id | `caveat-coverage-audit.md` §2 の `#` 列と同じ番号（1-100）。サブ項目（例: `20a`〜`20l`、`34b`、`37b/37c`、`54b`）は親の id の行に統合し、内容欄・根拠欄に含めた |
| 注意事項（短い名前） | audit 表の「注意事項」列を短縮した名前 |
| 伝えている内容（1文） | その注意事項が利用者に何を伝えるかの要約。原文がある場合は audit / tiers.md の引用を基にした |
| 出どころ（file:line / フィールド） | audit 表の「出どころ」列そのまま |
| 発火条件 | audit 表の「発火条件」列。掃引で見つかった最小の条件と件数 |
| 影響 | 「順位が変わる」「送れるかが変わる」「金額の確かさ」「前提・説明」のどれに効くか（複数該当時は主なもの1つ） |
| 今のUI（main）での表現 | audit 表の「今のUI」列を基にした、現行 main での見え方 |
| Mock v3 での表現 | `mock-v3-caveat-map.md` の「v3 form」「why」列と、audit の Mock(v2) 列（v3 map に個別記載が無い＝v2 から不変の項目）を統合したもの |
| **UI区分** | 下記5分類のいずれか1つ |
| 区分の根拠 | UI区分をその値にした理由。v3 map の "why" 列やグラマー文書の該当節を引用 |
| 必要なエンジンのフィールド | `caveat-ui-grammar.md` §5「エンジンに足すべき構造化フィールド」に載っている場合はそれを、無ければ `-` |
| リリース前に決めること | オーナーが最終的に判断すべき論点。無ければ `-` |
| 担当 | 空欄（オーナーが割り当てる） |
| 状態 | 全件 `未検討` |
| 最終更新日 | 台帳作成日 `2026-09-15`（個別行を見直したら更新すること） |

### UI区分の5分類

オーナー指示「今いい感じにUIに乗せられてるものと無理なものを区別」に基づく。`caveat-ui-grammar.md` の7手段（位置・線種・数字の書き方・区間の帯・記号・状態・動き）と `mock-v3-caveat-map.md` の実装状況を突き合わせて判定した。

- **形で表現できている** — 文字を読まずに形・位置・線・状態で伝わる（例: 線種、記号 `!`/`?`/`§`、帯のぼかし、ブラケット）
- **言葉で補っている** — 画面に出ているが、文字（1行・1句）に頼っている（形だけでは伝えきれない部分がある）
- **開いた中だけ** — 行を開く/カートを開く/§を押すまで見えない（根拠・仕組みの説明として意図的に段3に置かれているもの）
- **未表現（無理）** — 今の設計・データでは画面に乗せられない。理由を「区分の根拠」に、足りないエンジンのフィールドを「必要なエンジンのフィールド」に書いた
- **条件未発見** — 発火条件が見つからない、または Mock の入力手段では再現できず判定できない（audit の「条件未発見」「再現不能」をここに統合した）

### 更新ルール

1. `caveat-coverage-audit.md` / `caveat-ui-grammar.md` / `mock-v3-caveat-map.md` のいずれかが更新されたら、対応する id の行を見直し、「最終更新日」を更新する。
2. 実装（`src/components/compare/*` など）が変わって「今のUI（main）での表現」の実態が変わったら、その id の行だけを直す。台帳全体を作り直す必要はない。
3. 「状態」列はオーナー運用: `未検討` → `検討中` → `決定` / `保留` など、必要な値をオーナーが決めて使う（本ドキュメントでは値のセットを固定しない）。
4. 「担当」もオーナーが割り当てる。サブエージェントが自分の id を勝手に埋めない。
5. 確認できていない事実を推測で埋めない。分からなければ該当セルに「未確認」と書く（このルールは台帳作成時から一貫させる）。

### 既知の限界（台帳作成時点、2026-09-15）

- `caveat-coverage-audit.md` 自身が「#6 重量不明の段」「#94 primarySource」など、コードは存在するが今のデータでは発火しない（条件未発見）項目を含んでいる。これらは実装のバグではなく、判定できないという記録。
- `mock-v3-caveat-map.md` は audit の100件のうち Mock v2 から**変化があった項目・意図的に非表示にした項目**だけを記載している。台帳では「v3 map に記載が無い id」は「audit の Mock(v2) 列のまま v3 でも変化していない」とみなして統合した。この前提が崩れる更新（v3 map に書かれていない差分が実は生じていた等）があれば台帳の「Mock v3 での表現」列がずれる。
- PR #149（GB/DE の FedEx/UPS 着地通関手数料を埋めた）以降、id 71（着地通関手数料の額不明）が「条件未発見」のままかどうかは未確認。台帳ではその旨を区分の根拠欄に明記した。
